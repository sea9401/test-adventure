# 장애 대응 절차

이 문서는 게임 내용과 무관한 서버·DB·배포·백업·보안·운영 자동화 장애의 공통 절차다.
장애 중에는 원인 규명보다 사용자 영향 축소와 증거 보존을 우선한다.

## 등급과 목표

| 등급 | 기준 | 최초 확인 | 상태 공유 | 예시 |
|---|---|---:|---:|---|
| SEV-1 | 전체 접속 불가, 데이터 손상·유출 가능성 | 5분 | 15분마다 | DB 장애, 인증 전체 실패, 재화 대량 오지급 |
| SEV-2 | 핵심 기능 일부 불가, 다수 사용자 영향 | 15분 | 30분마다 | 전투 저장 실패, 길드·거래 중단 |
| SEV-3 | 우회 가능, 제한된 사용자 영향 | 4시간 | 중요 변경 시 | 특정 화면 오류, 지연 증가 |
| SEV-4 | 사용자 영향 없음, 예방 조치 | 다음 운영 점검 | 종료 시 | 감시 공백, 용량 추세 경고 |

## 역할

- **지휘자**: 등급·우선순위·점검 모드·복구 완료를 결정하고 타임라인을 유지한다.
- **조치자**: 로그와 지표를 확인하고 복구·롤백을 수행한다.
- **소통 담당**: 공지·문의 답변·운영 알림을 동일한 사실과 시각으로 맞춘다.
- 한 사람이 여러 역할을 맡아도 타임라인에는 각 결정을 구분해 기록한다.

## 최초 10분

1. 사용자 영향 범위, 시작 추정 시각, 최근 배포 SHA를 기록한다.
2. `/api/health`, 공개 표면, EC2/RDS 지표, systemd·cron·백업 로그를 확인한다.
3. 쓰기 작업이 데이터 손상을 키울 가능성이 있으면 `bash deploy/maintenance.sh on`으로
   차단한다. 점검 해제는 복구 검증 후 별도 승인으로만 수행한다.
4. 배포 직후 장애면 코드·스키마 호환성을 확인하고 `deploy/rollback.sh`를 검토한다.
5. 보안 사고 가능성이 있으면 관련 키를 삭제하기 전에 로그·CloudTrail·감사 기록을 보존한다.

## 복구 원칙

- 가장 작고 되돌릴 수 있는 조치를 먼저 사용한다.
- 운영 DB에서 진단용 파괴 쿼리를 실행하지 않는다.
- 마이그레이션 포함 배포는 코드 롤백만으로 복구됐다고 판단하지 않는다.
- 백업 복원은 원본을 덮지 않는 새 DB에서 먼저 검증하고 RPO·RTO를 기록한다.
- 재화·보상 교정은 계정 추적과 관리자 감사 로그가 남는 기존 운영 기능을 사용한다.

## 복구 완료 조건

- 내부 health와 실제 도메인의 핵심 공개 표면이 연속 3회 정상이다.
- DB 연결, 주요 쓰기 경로, 크론·백업 heartbeat가 허용 범위 안이다.
- 신규 오류와 사용자 영향이 15분 이상 증가하지 않는다.
- 데이터 정합성 검증과 미처리 보상 실패 확인이 끝났다.
- 점검 모드는 위 조건을 기록한 뒤 사용자의 별도 해제 지시가 있을 때만 끈다.

## 종료와 사후 분석

SEV-1은 2영업일, SEV-2는 5영업일 안에 `docs/templates/incident-report.md`를 작성한다.
개인의 실수보다 방어 장치가 왜 막지 못했는지를 설명하고, 각 후속 작업에 담당자·기한·검증
방법을 둔다. 같은 원인의 두 번째 장애부터는 자동 검증이나 구조 변경 없이는 종료하지 않는다.
