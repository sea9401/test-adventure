# 도감 숙련·월간 연구 출시 런북

이 문서는 B1~B10 로컬 구현을 운영에 반영할 때의 수동 순서다. 명령과 화면을 설명할 뿐 배포, 기능
플래그 변경, 백필, 시즌 예약, 결산, 트로피 발급, 명예 공개를 자동 실행하지 않는다. 배포와 점검 모드
해제는 각각 별도 승인 사항이며, 운영 배포·롤백 뒤에도 점검 모드는 자동으로 끄지 않는다.

## 1. 변경 전 정적 확인

1. 배포 대상 커밋에 Phase A 보류 브랜치나 별도 미배포 작업이 섞이지 않았는지 확인한다.
2. `npm run check:codex-mastery-release`로 도감 플래그 기본값 전부 `false`, B10 공개 경계와 API·UI,
   `PUBLISH` 확인 문자열, 도감 전용 cron·실운영 시즌 정의 부재를 확인한다.
3. `npm run check-migrations`, `npm run check-images`, 타입 검사, 전체 테스트와 빌드를 새로 실행한다.
4. 0171~0175 마이그레이션 순서와 백업·복구 지점을 확인한다. 0175는 `published_at`과 채널별 공개
   원장을 추가하며 기존 종료 시즌을 자동 공개하지 않는다.

## 2. 배포 직후 비활성 확인

DB의 `codex-mastery-features.v1` 값을 읽어 다음 항목이 모두 꺼져 있는지 확인한다.

```text
recordingEnabled, overviewVisible, rankingVisible, sealsEnabled,
trophiesEnabled, monthlyProgressEnabled, monthlyRankingVisible,
settlementEnabled, feedEnabled
```

공개 랭킹 API가 `enabled: false`이고 도감 연구 시즌, 진행, 트로피, 공개 원장이 비어 있거나 예상한
시험 데이터만 갖는지 읽기 쿼리로 확인한다. 이 단계에서 백필이나 시즌 생성은 실행하지 않는다.

## 3. 기초 데이터 복구와 백필

1. 먼저 dry-run으로 도감 요약 복구 대상과 예상 변경량을 기록한다.
2. 소수 내부 계정에만 적용해 원본 이벤트와 요약이 일치하는지 확인한다.
3. 전체 적용 전 DB 백업 시각과 되돌릴 범위를 기록한다.
4. 적용 뒤 복구 명령을 다시 dry-run해 변경 예정 0건인지 확인한다.
5. 트로피 재구축도 별도 dry-run과 승인 후 수행한다. 월간 연구 트로피는 시즌 결산 전 만들지 않는다.

## 4. 단계별 기능 공개

한 단계마다 오류율, 응답 시간, 기록 증가량과 사용자 문의를 관찰하고 다음 단계로 넘어간다.

1. 영구 도감 기록 수집
2. 개인 개요
3. 영구 숙련 랭킹
4. 인장·트로피 표시
5. 월간 진행 기록(공개 랭킹은 계속 닫음)
6. 내부 시험 시즌

기능을 켜는 실제 작업은 이 런북과 별도의 운영 승인·감사 기록으로 실행한다.

## 5. 월간 시즌 운영 순서

1. 다음 KST 월의 정의 JSON을 운영 화면에서 검증한다.
2. `SCHEDULE YYYY-MM`로 미래 시즌만 예약한다.
3. 진행 중에는 월간 공개 랭킹을 닫은 채 기록량과 이상치를 관찰한다.
4. 종료 뒤 결산 미리보기로 참가 수, 상위 순위, 등급 수를 검토한다.
5. 필요하면 트로피가 없고 아직 공개되지 않은 동안만 `RESETTLE YYYY-MM`을 사용한다.
6. `SETTLE YYYY-MM`로 최종 순위·등급을 저장한다.
7. 저장 결과와 미리보기가 일치할 때 `AWARD YYYY-MM`로 트로피를 멱등 발급한다.
8. 트로피 이력과 최종 등급이 정확히 일치하는지 확인한 뒤 `PUBLISH YYYY-MM`로 개인 알림과 명예의
   전당을 공개한다. `feedEnabled`가 켜져 있을 때만 다이아·전설을 전체 소식·전광판에 기록한다.
9. 최초 공개 때 전체 소식이 꺼져 있었다면 나중에 플래그 승인 후 같은 `PUBLISH`를 다시 실행한다.
   원장이 개인 알림 중복을 막고 누락된 전체 소식만 채운다.

## 6. 중단과 되돌림 경계

- 결산 전: 시즌 정의와 플래그를 확인하고 작업을 중단할 수 있다.
- 결산 후·트로피 전: 공개되지 않았고 트로피가 0건일 때만 재결산할 수 있다.
- 트로피 후·공개 전: 결과를 다시 쓰지 말고 불일치 원인을 조사한다.
- 공개 후: `published_at`이 권위 경계다. 트로피가 0건이어도 재결산하지 않는다. 공개 행이나 순위를
  직접 수정하지 말고 새 코드·데이터 복구 절차를 별도 승인받는다.
- 공개 트랜잭션 실패: 시즌 시각, 공개 원장, 개인 알림, 전체 소식이 함께 롤백됐는지 확인한 뒤 같은
  `PUBLISH`를 재실행한다.

## 7. 공개 후 관찰

- 종료 시즌 API에는 `closed AND published_at IS NOT NULL` 시즌만 보이는지 확인한다.
- 저장된 `final_rank`의 빈 순번이 차단·이름 없음 필터 뒤에도 다시 매겨지지 않는지 확인한다.
- 공개 원장의 `notification` 수와 개인 알림 수, `feed` 수와 다이아·전설 전체 소식 수를 비교한다.
- 중복 알림·중복 전광판, 공개 뒤 재결산 성공, 비공개 시즌 노출이 한 건이라도 있으면 다음 공개를
  중단한다.
- 브라우저 푸시는 B10의 전달 보장 범위가 아니다. DB 개인 알림을 권위 결과로 본다.
