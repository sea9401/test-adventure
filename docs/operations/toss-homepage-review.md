# 토스페이먼츠 홈페이지 심사 준비

이 문서는 무슨 코인 상품의 토스페이먼츠 홈페이지 심사를 준비하는 절차다. 심사 준비와
실제 유료 판매 출시는 별개다. 사용자의 명시적인 배포 지시 전에는 어떤 환경에도 적용하지
않으며, 테스트 키를 쓰는 심사 기간에도 일반 이용자의 코인 상점은 닫아 둔다.

## 2026-09-04 진행 체크포인트

완료된 항목:

- 공개 무슨 코인 상품 페이지와 네 상품별 고유 이미지 구성
- 대문·상품 페이지 사업자 정보 표시 구성
- 대표자명, 사업장 주소, 공개 연락처를 운영 공개 설정에 반영
- Toss Payments SDK v2 결제창 이벤트 흐름과 결제·환불 서버 기능 구현
- 같은 MID에서 발급된 `test_gck_`·`test_gsk_` 테스트 키 세트 보유 확인
- 토스페이먼츠에 계정 귀속형 게임 재화의 심사용 계정 허용 여부 문의 이메일 발송
- 토스페이먼츠 회신으로 회원 전용 결제 화면은 입점·홈페이지 심사 때 요청받은 테스트
  계정을 제출하는 방식임을 확인
- 운영 DB 읽기 전용 점검으로 `gcrb-review-01`~`03` 계정이 모두 존재하고 비활성화·제재
  상태가 아님을 확인 (`01`·`02`는 프로필 준비됨, `03`은 프로필 미설정)
- 운영 SSM에 기존 `REVIEW_LOGIN_*` 세 값이 함께 설정되어 있음을 값 비노출로 확인
- 토스 제출 계정으로 `gcrb-review-01`을 선택하고 새 scrypt 비밀번호 해시로 교체한 뒤 기존
  활성 세션을 초기화함 (평문 비밀번호는 출력·저장하지 않고 사용자 클립보드에만 전달)

재개할 때 확인할 항목:

1. 운영 로그인 화면에서 `gcrb-review-01`과 사용자 클립보드의 새 비밀번호로 실제 로그인을
   확인한다.
2. 계약 신청, 가입비 결제와 서류 심사를 진행한다. 게임 내 충전성 재화는 유의 업종이라
   최종 입점 가능 여부는 계약 담당부서의 실제 심사에서 결정된다.
3. 같은 세트의 Toss 테스트 키를 Git이 아닌 운영 SSM SecureString에 등록한다.
4. 사용자가 명시적으로 심사용 배포를 요청한 뒤에만 홈페이지 심사 모드와 테스트 결제를
   활성화해 배포한다.
5. 선택한 심사 계정의 기존 활성 세션을 제출 직전에 비우고, 외부에서 상품·사업자 정보·정책
   링크·로그인·테스트 결제창을 확인한 뒤 심사 URL과 계정을 안전한 채널로 전달한다.

현재 배포와 키 등록은 수행하지 않았다. 운영 기본값은 상점 비공개, 결제 비활성,
홈페이지 심사 모드 비활성이다. 실제 테스트 키와 심사용 비밀번호는 이 문서에 저장하지 않는다.

운영 SSM의 기존 `REVIEW_LOGIN_*`은 카카오 계정에 연결하는 호환 경로이며, 2026-09-04 점검
기준 해당 대상은 코인 상점 허용 목록과 일치하지 않았다. 토스에는 코인 상점 접근이 이미
허용된 별도 `password_credentials` 계정 `gcrb-review-01` 또는 `gcrb-review-02`를 제출한다.
현재 제출 대상으로 정한 `01`은 비밀번호를 교체하면서 `active_session_id`를 비웠다. 대체 계정
`02`에는 기존 활성 세션이 있으므로 실제 제출 대상으로 바꿀 때만 해당 세션을 비운다.

## 현재 공개 표면

- 대문: `/sign-in`
- 판매 상품: `/products/museun-coin`
- 이용약관과 환불 기준: `/terms`
- 개인정보처리방침: `/privacy`
- 실제 구매 화면: `/settings/coin-shop` (로그인한 심사 계정만 접근)

판매 상품 화면에는 1,000·2,000·3,000·5,000 코인 상품, 원화 가격, 서로 다른 상품 이미지,
결제 승인 후 즉시 지급, 계정 귀속과 환전 금지, 환불 기준 링크를 표시한다. 대문과 상품
화면에는 상호와 사업자등록번호를 표시하며, 아래 환경 변수까지 입력하면 대표자·주소·연락처도
함께 표시한다.

## 아직 받아야 할 실제 값

사업자등록증과 신청서에 적은 내용 그대로 다음 값을 준비한다. 임의 값이나 예시 값으로
심사를 요청하지 않는다.

| 환경 변수 | 입력할 내용 | 공개 여부 |
| --- | --- | --- |
| `PUBLIC_MERCHANT_REPRESENTATIVE` | 사업자등록증의 대표자명 | 공개 |
| `PUBLIC_MERCHANT_ADDRESS` | 사업자등록증의 사업장 주소 | 공개 |
| `PUBLIC_MERCHANT_CONTACT` | 구매자 문의를 받을 전화번호 | 공개 |
| `PUBLIC_MERCHANT_MAIL_ORDER_SALES_NUMBER` | 발급된 경우 통신판매업 신고번호 | 공개·선택 |

상호 `무슨게임`과 사업자등록번호 `781-52-01091`은 공개 상수로 관리한다. 실제 값이 달라지면
심사 배포 전에 코드와 등록증을 대조해 수정한다.

## 심사 전 비밀 설정

비밀값은 Git, 문서, 채팅, 브라우저 코드에 넣지 않고 운영 비밀 저장소에만 등록한다.

```dotenv
NEXT_PUBLIC_MUSEUN_COIN_SHOP_OPEN=false
PG_HOMEPAGE_REVIEW_MODE=true
MUSEUN_COIN_PAYMENTS_MODE=test
TOSS_PAYMENTS_CLIENT_KEY=<test_gck로 시작하는 결제 클라이언트 키>
TOSS_PAYMENTS_SECRET_KEY=<같은 세트의 test_gsk 시크릿 키>

REVIEW_LOGIN_ID=<심사자용 로그인 ID>
REVIEW_LOGIN_PASSWORD=<12자 이상 임시 비밀번호>
REVIEW_LOGIN_USER_EMAIL=<기존 심사 계정 이메일>
MUSEUN_COIN_SHOP_REVIEW_USER_IDS=<해당 계정의 users.id>
```

클라이언트 키와 시크릿 키는 반드시 같은 상점·같은 세트의 테스트 키를 쓴다. 시크릿 키에는
`NEXT_PUBLIC_` 접두사를 붙이지 않는다. 심사 계정은 실제 구매 화면에만 필요하며 공개 상품과
정책 화면은 로그인 없이 열려야 한다. 계정 귀속형 게임 재화라 비회원에게 지급할 수 없다는
점과 심사 계정을 토스 신청 메모 또는 심사 담당자에게 안전한 채널로 전달한다.

## 배포 직전 점검

1. 사업자 정보가 사업자등록증과 일치하는지 확인한다.
2. `/products/museun-coin`에서 네 상품 이미지가 모두 보이고 깨진 이미지나 빈 목록이 없는지 확인한다.
3. 대문 푸터에서 상호·등록번호·대표자·주소·연락처를 확인한다.
4. 심사 계정으로 로그인한 뒤 `/settings/coin-shop`에 접근되는지 확인한다.
5. `node scripts/check-production-env.mjs`가 전체 운영 환경에서 통과하는지 확인한다.
6. 결제창에서 신청한 카드·간편결제 수단이 보이는지 확인한다.

일반 운영 배포 절차를 사용한다. 정확한 `main` SHA의 CI와 운영 산출물이 준비된 뒤 런타임
교체 직전에만 배포 워크플로가 점검 모드를 켜게 하며, 배포가 끝났다고 점검 모드를 자동으로
해제하지 않는다.

## 테스트 결제 확인

1. 각 상품 중 하나로 결제창을 열고 주문명과 금액을 확인한다.
2. 결제창을 닫은 뒤 버튼이 다시 활성화되는지 확인한다.
3. 테스트 결제를 완료해 성공 URL로 이동하고 코인이 한 번만 지급되는지 확인한다.
4. 새로고침과 성공 URL 재호출로 중복 지급되지 않는지 확인한다.
5. 실패 결제로 실패 URL과 주문 상태를 확인한다.
6. 결제 내역에서 미사용 코인 환불 요청과 운영자 환불 검토 흐름을 확인한다.
7. 토스 개발자센터의 테스트 결제 내역과 내부 주문번호·금액·상태를 대조한다.

실제 카드 대금이 움직이는 라이브 키로 홈페이지 심사를 시험하지 않는다.

## 심사 종료 후

실제 출시를 별도로 승인받기 전까지 다음 상태로 되돌린다.

```dotenv
PG_HOMEPAGE_REVIEW_MODE=false
NEXT_PUBLIC_MUSEUN_COIN_SHOP_OPEN=false
MUSEUN_COIN_PAYMENTS_MODE=disabled
```

심사 계정 비밀번호는 회전하거나 비활성화하고 더 이상 필요 없는 테스트 시크릿은 운영 비밀
저장소에서 제거한다. 공개 상품 페이지와 사업자 고지는 유지할 수 있다. 라이브 결제 전환은
카드사 심사 완료, 약관 시행일 공지, 웹훅, 환불·장애 대응 확인을 마친 뒤 별도 변경과 별도
배포로 진행한다.
