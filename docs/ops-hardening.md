# 운영 방어 점검 메모

## 적용된 방어선

- 이상 행동 로그: 반복 제한 초과를 `abuse_events`에 저장하고 관리자 `이상 행동` 탭에서 조회한다.
- 유저+IP 제한: 주요 반복 액션은 유저 단위 제한과 IP 단위 제한을 같이 본다.
- 거래소/상점 제한: 구매, 판매, 등록, 취소, 시세/최근 거래 조회에 API 제한을 적용했다.
- `me/state` 부하 완화: 거점/자유 타일 정착지 조회는 짧은 in-memory cache로 중복 DB 조회를 줄인다.
- 거래소 조회 캐시: 시세는 30초, 최근 거래는 15초 캐시한다.
- 관리자 감사 로그: 저장 데이터 직접 수정과 길드 쿨다운 해제도 `admin_audit_log`에 남긴다.
- 중복 클릭 방지: 상점, 거래소, 낚시, 발굴의 주요 변경 액션은 클라이언트에서도 단일 실행으로 잠근다.
- 경제 로그: 거래소, 상점, 주요 보상 수령 이벤트를 `economy_events`에 남기고 관리자 `경제 로그` 탭에서 조회한다.
- 경제 요약: 관리자 `경제 로그` 탭에서 필터 결과 기준 재화별 증감, 시간대별 이벤트, 유저별 골드 흐름을 확인한다.
- 보상/숙련 이력: 유저 상세의 `운영 요약`에서 최근 보상 수령, 보상 실패, 숙련/증서 이벤트를 확인한다.
- 낚시 일일 제한: 낚시 화면에 오늘 챔질 코인 획득량/남은량/상한 도달 문구를 표시한다.
- 운영 현황판: 관리자 `운영 현황` 탭에서 최근 제한 초과, 경제 이벤트, 관리자 변경 흐름, 임계치 알림을 확인한다.
- 운영 알림: `OPS_ALERT_WEBHOOK_URL`이 있으면 action 그룹별 제한 초과, 보상 실패, 대량 골드 이동, 일일 리포트를 웹훅으로 보낸다.
- 이벤트 설정: 관리자 `운영 현황` 탭에서 핫타임 기간/배율/메모를 저장하고 감사 로그에 남긴다.
- 핫타임 적용: 활성 기간에는 사냥 골드/EXP, 길드 훈련 숙련도, 낚시 코인 보너스가 실제 보상에 적용된다.
- 경제 CSV: 관리자 `경제 로그` 탭에서 현재 필터 결과를 CSV로 내려받는다.
- 보상 보정: 유저 상세 `운영 요약`에서 골드, 낚시/발굴 코인, 숙련 증서, 스태미나 회복약, 재료를 보정 지급한다.
- 매크로 점수: 운영 현황에서 제한 이벤트, action 다양성, IP 수를 합산한 의심 점수를 본다.
- 보관 정책: `/api/v2/cron/ops-retention`이 오래된 운영 로그를 정리한다.
- 일일 리포트: `/api/v2/cron/ops-daily-report`가 최근 24시간 제한/경제/보상 실패/관리자 변경 요약을 알림으로 보낸다.
- 배포 스모크: 배포 후 `/api/v2/cron/deploy-smoke`가 운영 로그/설정 테이블 조회 가능 여부를 확인한다.

## 제한 기준

- 전투/강화처럼 정상 반복이 잦은 API는 분당 유저 90~180회, IP 500~900회 수준으로 둔다.
- 거래소/상점의 변경 API는 분당 유저 30~90회, IP 180~540회 수준으로 둔다.
- 조회 API는 캐시가 있는 경우에도 분당 유저 120~180회, IP 800~1000회로 둔다.
- 발굴/낚시/숙련의 탑은 미니게임 흐름상 정상 클릭 속도를 고려해 변경 API에 유저+IP 제한을 둔다.

## 느린 쿼리 후보

- `marketplace_listings_v2`의 판매 완료 집계: 시세 조회가 최근 N일 sold row를 스캔하므로 캐시했다.
- `marketplace_listings_v2`의 최근 거래: 최신 sold row 정렬 조회라 캐시했다.
- `me/state`의 현재 거점/자유 타일 정착지: 여러 화면에서 반복 호출되어 짧은 캐시를 적용했다.
- 랭킹류 API: 기존 in-flight dedup/cache가 있어 추가 변경은 하지 않았다.

## 운영 시 확인할 값

- `OPS_ALERT_WEBHOOK_URL`: Slack/Discord 호환 웹훅 URL. 없으면 알림은 비활성화된다.
- `abuse_events`: 같은 IP에서 여러 유저가 동일 API에 걸리는지 확인한다.
- `economy_events`: 거래소/상점/보상 이벤트의 골드·아이템 흐름을 확인한다.
- `ops_settings`: 핫타임/이벤트 운영 설정을 확인한다.
- `admin_audit_log`: 운영자가 직접 바꾼 저장 데이터와 쿨다운 해제 이력을 확인한다.
- `src/lib/server/rateLimitStore.ts`: Redis 이전 시 교체할 저장소 인터페이스.

## 문의 대응 순서

### 보상이 안 들어왔다

1. 관리자 `유저` 탭에서 대상 유저를 선택한다.
2. `운영 요약`의 `최근 보상 수령`과 `숙련/증서 이벤트`를 확인한다.
3. 없으면 `경제 로그`에서 `userId`로 필터링하고 `reward.failure.*` 이벤트가 있는지 본다.
4. 낚시 코인은 화면의 `오늘 챔질 코인`이 상한에 도달했는지 확인한다. 상한 도달 후 챔질 코인은 미지급이 정상이다.
5. 관리자 보정 지급이 필요하면 `v2 지급`을 사용하고, 이후 `감사 로그`와 `운영 요약`에 기록됐는지 확인한다.
6. 보상 실패 로그 기준으로 보정할 때는 `운영 요약`의 보상 보정 지급에 원본 event id와 사유를 남긴다.

### 매크로/과부하가 의심된다

1. `운영 현황`의 알림 카드에서 최근 5분/1시간 제한 초과를 본다.
2. `운영 현황`의 매크로 의심 점수 Top을 확인한다.
3. `이상 행동` 탭에서 action, reason, IP, userId 필터로 같은 패턴이 반복되는지 확인한다.
4. 같은 IP에서 여러 계정이 짧은 시간에 걸리면 IP 제한/제재 후보로 본다.
5. 한 계정만 특정 변경 API를 반복하면 유저 제재 또는 해당 API 제한값 조정을 검토한다.
6. 정상 반복 플레이도 걸리면 `userRateLimit.ts`의 group threshold와 API별 limit/window를 완화한다.

## 보관 정책

- `abuse_events`: 90일 보관.
- `economy_events`: 180일 보관.
- `ops_settings`: 현재 설정 보관. 이력은 `admin_audit_log`로 추적한다.
- 1회 삭제 상한은 5,000행이다. 오래 쌓였으면 다음 cron 이 이어서 정리한다.

## 다음 단계 후보

- 서버가 여러 인스턴스로 늘어나면 `rateLimitStore`의 memory 구현을 Redis 구현으로 교체한다.
- 실제 알림량을 보고 그룹별 `threshold`와 `windowMs`를 더 세분화한다.
