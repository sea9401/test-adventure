# 운영 방어 점검 메모

## 적용된 방어선

- 이상 행동 로그: 반복 제한 초과를 `abuse_events`에 저장하고 관리자 `이상 행동` 탭에서 조회한다.
- 유저+IP 제한: 주요 반복 액션은 유저 단위 제한과 IP 단위 제한을 같이 본다.
- 거래소/상점 제한: 구매, 판매, 등록, 취소, 시세/최근 거래 조회에 API 제한을 적용했다.
- `me/state` 부하 완화: 거점/자유 타일 정착지 조회는 짧은 in-memory cache로 중복 DB 조회를 줄인다.
- 거래소 조회 캐시: 시세는 30초, 최근 거래는 15초 캐시한다.
- 관리자 감사 로그: 저장 데이터 직접 수정과 길드 쿨다운 해제도 `admin_audit_log`에 남긴다.
- 중복 클릭 방지: 상점, 거래소, 낚시, 발굴의 주요 변경 액션은 클라이언트에서도 단일 실행으로 잠근다.
- 운영 알림: `OPS_ALERT_WEBHOOK_URL`이 있으면 같은 API의 제한 초과가 5분 내 25회 이상 누적될 때 웹훅 알림을 보낸다.

## 제한 기준

- 전투/강화처럼 정상 반복이 잦은 API는 분당 유저 90~180회, IP 500~900회 수준으로 둔다.
- 거래소/상점의 변경 API는 분당 유저 30~90회, IP 180~540회 수준으로 둔다.
- 조회 API는 캐시가 있는 경우에도 분당 유저 120~180회, IP 800~1000회로 둔다.
- 발굴/낚시/숙련의 탑은 미니게임 흐름상 정상 클릭 속도를 고려해 변경 API에 유저+IP 제한을 둔다.

## 느린 쿼리 후보

- `marketplace_listings_v2`의 판매 완료 집계: 시세 조회가 최근 N일 sold row를 스캔하므로 캐시했다.
- `marketplace_listings_v2`의 최근 거래: 최신 sold row 정렬 조회라 캐시했다.
- `me/state`의 현재 거점/자유 타일 정착지: 여러 화면에서 반복 호출되어 짧은 캐시를 적용했다.
- 랭킹류 API: 기존 in-flight dedup/cache가 있어 추가 변경은 하지 않았다.

## 운영 시 확인할 값

- `OPS_ALERT_WEBHOOK_URL`: Slack/Discord 호환 웹훅 URL. 없으면 알림은 비활성화된다.
- `abuse_events`: 같은 IP에서 여러 유저가 동일 API에 걸리는지 확인한다.
- `admin_audit_log`: 운영자가 직접 바꾼 저장 데이터와 쿨다운 해제 이력을 확인한다.

## 다음 단계 후보

- 서버가 여러 인스턴스로 늘어나면 현재 in-memory rate limit을 Redis 기반으로 옮긴다.
- `abuse_events`가 커지면 월 단위 보관 정책이나 오래된 row 삭제 cron을 둔다.
- 실제 알림량을 보고 `threshold`와 `windowMs`를 API별로 분리한다.
