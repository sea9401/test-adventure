# 서비스 목표(SLO)와 운영 지표

운영 화면의 SLO 카드는 목표와 관측 가능 여부를 함께 보여준다. 데이터가 없거나 수집기가
꺼져 있으면 `정상`으로 간주하지 않고 `측정 대기`로 표시한다.

| 목표 | 기준 | 창 | 현재 데이터 소스 |
|---|---:|---:|---|
| 공개 서비스 가용성 | 99.9% 이상 | 최근 30일 | GitHub 외부 uptime monitor |
| API 응답 p95 | 1,000ms 이하 | 최근 런타임 표본 | 서버 runtime profiler |
| API 오류율 | 1% 미만 | 최근 런타임 표본 | 서버 runtime profiler |
| DB 백업 최신성 | 30시간 이내 | 현재 | `backup:database` heartbeat |
| 중요 크론 최신성 | 15분 이내 | 현재 | 중요 cron heartbeat |

## 판정 방식

- API p95는 요청이 존재하는 기능별 p95 중 가장 느린 값을 사용한다. 평균으로 빠른 경로가
  느린 경로를 가리지 않도록 보수적으로 판정한다.
- API 오류율은 runtime profiler 표본의 전체 요청 대비 HTTP 5xx·중단 요청 비율이다.
- runtime profiler는 프로세스 단위 메모리 집계이므로 앱 재시작 때 현재 표본이 초기화된다.
  표본이 없으면 `측정 대기`가 정상 동작이다.
- 백업·크론 heartbeat는 systemd 자원 감시가 판정해 운영 webhook으로 알린다. 현재 관리자
  UI에는 서버 파일 상태를 직접 노출하지 않으므로 목표 카드는 `측정 대기`로 표시되고,
  실제 위반 여부는 운영 알림과 journal에서 확인한다.
- 공개 가용성의 30일 누적치는 외부 모니터가 원본이다. 저장소 내부 감시만으로 계산하지
  않으며, 외부 상태 제공자를 연결하기 전까지 UI는 `측정 대기`로 둔다.

## 오류 예산

99.9% 월간 가용성 목표의 허용 중단 시간은 30일 기준 약 43분이다. 계획 점검도 사용자에게
서비스를 제공하지 못한 시간이라면 원칙적으로 오류 예산에 포함한다. 단, 지표 공급자 장애와
실제 서비스 장애는 사건 기록에서 구분한다.

오류 예산의 절반을 소진하면 고위험 기능 배포를 줄이고 원인 제거를 우선한다. 전부 소진하면
긴급 보안 수정 외의 운영 배포를 보류하고 복구·재발 방지 작업을 먼저 진행한다.

## 운영 점검

1. 매일 운영 요약에서 목표 초과와 `측정 대기` 항목을 확인한다.
2. 매주 외부 uptime, runtime profiler, heartbeat 알림을 대조한다.
3. 매월 가용성·오류 예산·가장 느린 API·감시 공백을 사건 기록에 남긴다.
4. 임계치를 바꿀 때는 수치와 이유를 같은 커밋에서 갱신하고 운영 변경 체크리스트를 따른다.
