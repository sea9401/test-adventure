# RDS 부하 절감과 자동 복구 설계

## 목표

2026-08-09 `db.t4g.micro` 메모리 고갈 사고에서 확인된 반복 조회 부하를 줄이고, RDS가 재시작돼도 앱이 고착된 연결을 계속 사용하지 않게 하며, 동일한 메모리 압박을 운영 웹훅으로 조기에 알린다. RDS 등급 변경과 배포는 이번 범위에 포함하지 않는다.

## 폴링 부하 절감

- 기본 채팅(global/trade/guild)은 클라이언트에서 세 요청을 병렬 호출하지 않고 `/api/chat?channels=main` 한 번으로 조회한다.
- 서버는 인증, 차단 목록, 길드 확인, 외형 조회를 요청당 한 번만 수행하고 채널별 메시지를 묶어 반환한다. 기존 단일 채널 API와 커스텀 채팅방 API 계약은 유지한다.
- 기본 채팅은 패널이 열렸을 때 3초, 닫혔을 때 30초마다 조회하고 숨겨진 탭에서는 기존처럼 멈춘다.
- 접속 하트비트는 15초에서 30초, 제재 상태 확인은 30초에서 2분으로 늘린다. 제재 적용 자체는 모든 게임 API의 `ensureUser`가 계속 즉시 차단하므로 보안 경계는 바뀌지 않는다.

## DB 연결 자동 복구

- 프로세스 전역에서 하나의 `pg.Pool` 런타임을 공유해 Next.js 라우트 번들별 중복 풀 생성을 막는다.
- 기존 서버 측 `statement_timeout`과 별도로 `query_timeout=15초`를 둔다. RDS가 TCP 연결만 남긴 채 응답하지 않아도 클라이언트가 쿼리를 실패시키고 일반 `Pool.query` 경로에서 해당 연결을 폐기할 수 있다.
- TCP keepalive를 켜고 애플리케이션 이름을 지정해 장애 감지와 RDS 세션 식별을 개선한다.
- `/api/health`의 3초 DB 핑이 실패하면 현재 풀을 런타임에서 즉시 분리하고 비동기로 종료한다. 다음 요청은 새 풀을 만들며, 연속 헬스 요청에 의한 풀 회전 폭주를 막기 위해 30초 재생성 쿨다운을 둔다.

## RDS 메모리 경보

- 기존 `adventure-resource-monitor.timer`의 2분 주기를 재사용한다.
- 새 Node 스크립트가 CloudWatch `AWS/RDS FreeableMemory`의 최근 5분 최솟값을 조회한다.
- 기본 임계치는 192 MiB이며, 상태 변경 즉시·지속 시 30분마다 기존 운영 웹훅으로 경고하고 회복 시 한 번 알린다.
- EC2 역할에는 `cloudwatch:GetMetricStatistics` 읽기 권한만 추가한다. 권한 정책은 저장소에 명시하고 운영자가 배포 전에 적용한다.
- CloudWatch 조회 실패는 게임 서비스나 기존 EC2 자원 감시를 실패시키지 않고 journal에 명확히 남긴다.

## 검증

- 채팅 묶음 URL/응답 병합과 폴링 정책을 단위 테스트한다.
- DB 런타임이 풀을 한 번만 만들고, 회전 후 새 풀을 사용하며, 쿨다운을 지키는지 단위 테스트한다.
- RDS 메모리 감시 스크립트를 주입된 CloudWatch 응답과 임시 상태 파일로 실행해 경고·중복 억제·회복을 검증한다.
- 관련 Vitest, TypeScript, ESLint 및 전체 테스트를 실행한다.
