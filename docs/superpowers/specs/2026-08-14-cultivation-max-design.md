# 가능한 만큼 수행 설계

## 목적

수행 초기화 후 환급된 숙달 포인트를 다시 쓰기 위해 `수행` 버튼을 반복해 눌러야 하는 불편을 없앤다. 기존 1회 수행은 유지하고, 현재 보유한 숙달 포인트로 가능한 수행을 한 번에 처리하는 `가능한 만큼 수행` 동작을 추가한다.

## 사용자 경험

- 수행 카드의 기존 `수행` 버튼 옆에 `가능한 만큼 수행` 버튼을 배치한다.
- 하나의 수행 비용도 낼 수 없거나, 직업이 없거나, 생활직이거나, 이미 처리 중이면 두 버튼을 동일하게 비활성화한다.
- 처리 중에는 일괄 버튼을 `수행 중…`로 표시해 중복 요청을 막는다.
- 완료 메시지에 실제 수행 횟수, 총 소모 숙달 포인트, 대성공·각성 횟수, 성장 재분배량을 요약한다. 0인 특별 결과나 재분배량은 생략한다.
- 완료 후 스탯 한계, 수행 횟수, 잔여 포인트, 다음 비용, 환급 가능 포인트를 서버 응답의 최종 상태로 갱신한다.

## 서버 처리

기존 `POST /api/v2/me/cultivate`는 본문이 없으면 수행 1회를 처리하는 호환성을 유지한다. `{ "mode": "max" }` 본문을 받으면 같은 DB 트랜잭션과 잠금 안에서 아래를 반복한다.

1. 현재 한계 증가 합으로 다음 비용을 계산한다.
2. 현재 잔액으로 비용을 낼 수 없으면 종료한다.
3. 기존 `applyCultivation`을 호출해 대성공·각성 배수, 한계 증가, 성장 재분배, 실제 비용을 한 회분 적용한다.
4. 횟수와 합계를 누적하고, 갱신된 상태로 다음 반복을 진행한다.

이 순차 처리로 특별 수행이 다음 비용을 바꾸는 현재 규칙을 그대로 보존한다. 모든 수행은 한 트랜잭션에서 커밋하므로 일부만 저장되는 상태를 만들지 않는다. 수행 0회인 경우는 기존 `insufficient_proficiency` 응답을 유지한다.

비정상적으로 큰 잔액이 트랜잭션을 장시간 점유하지 않도록 요청당 최대 10,000회를 처리한다. 상한에 도달한 뒤에도 다음 비용을 낼 수 있으면 응답의 `hasMore`를 `true`로 내리고, 완료 메시지에 남은 포인트로 다시 수행할 수 있음을 알린다.

## 응답과 부가 효과

성공 응답에 기존 최종 상태 필드와 함께 다음 일괄 요약을 추가한다.

- `performed`: 실제 수행 횟수
- `spent`: 총 소모 숙달 포인트
- `greatSuccesses`: 3배 대성공 횟수
- `awakenings`: 5배 각성 횟수
- `redistributedGrowthPoints`: 총 재분배 성장 포인트
- `hasMore`: 요청당 안전 상한 도달 후에도 다음 수행 비용을 낼 수 있는지

1회 수행 응답에도 같은 요약 필드를 내려 클라이언트가 하나의 응답 형식을 사용하게 하되, 기존 `mult` 필드는 호환성을 위해 유지한다.

각성 전광판 소식은 트랜잭션 커밋 후 발생한 각성 횟수만큼 기존 이벤트를 기록해, 한 번씩 누르던 경우와 게임 결과를 동일하게 유지한다. 전광판 기록 실패는 기존처럼 수행 결과를 되돌리지 않는다.

## 오류 처리

- 미인증, 무직업, 생활직, 숙달 포인트 부족은 기존 오류 코드와 문구를 유지한다.
- 트랜잭션 도중 오류가 나면 전체 일괄 수행을 롤백한다.
- 클라이언트는 `busy` 상태로 1회·일괄 수행과 초기화의 동시 요청을 막는다.

## 테스트

- 도메인 테스트: 비용이 부족해질 때까지 반복하고, 각 회의 RNG 배수로 다음 비용과 최종 상태가 달라지는지 검증한다.
- 라우트 테스트: 기존 본문 없는 1회 요청과 `mode: "max"` 일괄 요청의 응답, 저장 결과, 각성 소식 횟수, 0회 오류, 안전 상한과 `hasMore`를 검증한다.
- UI 테스트: 버튼 활성 조건, `mode: "max"` 요청, 완료 요약, 최종 상태 갱신을 검증한다.

## 비범위

- 수행 비용, 대성공·각성 확률, 스탯 프로필, 초기화 비용은 바꾸지 않는다.
- 사용자가 숫자를 직접 입력하거나 고정 횟수 프리셋을 고르는 기능은 추가하지 않는다.
- 배포와 점검 모드 변경은 하지 않는다.
