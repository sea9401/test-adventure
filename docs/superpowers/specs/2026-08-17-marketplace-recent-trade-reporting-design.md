# 거래소 최근 체결 공개·신고 설계

## 배경

거래소는 이미 `marketplace_listings_v2`의 판매 완료 행을 보관하며, 서버에는
판매자·구매자 식별자를 제외한 전체 최근 체결 조회도 있다. 그러나 현재 화면은
`내 거래 > 거래 내역`에서 본인 체결만 불러오므로 일반 이용자가 시장 전체의 수상한
거래를 발견하고 신고할 수 없다.

또한 구매 화면의 재료·일부 소모품은 동일 품목 매물을 묶어 자동구매 대상으로
표시한다. 이 묶음을 만들 때 본인 매물을 올바르게 제외하지만, 제외한 매물을 별도
카드에도 넣지 않아 구매 화면 검색 결과에서 본인 스택 매물이 사라진다. 장비와
경매 매물은 이미 개별 카드로 노출된다.

## 목표

- 거래소 이용자가 시장 전체의 최신 체결 100건을 확인할 수 있게 한다.
- 판매자·구매자의 이름과 계정 식별자는 공개하지 않는다.
- 각 공개 체결을 거래소에 맞는 사유로 신고할 수 있게 한다.
- 운영자가 신고 당시 거래와 양쪽 계정을 함께 조사할 수 있는 증거를 보존한다.
- 기존 신고함, 중복 방지, 요청 제한과 운영 알림을 재사용한다.
- 구매 화면에서 본인이 등록한 재료·소모품 매물도 검색하고 관리할 수 있게 한다.
- 본인 매물은 자동구매 재고·가격·견적에 포함하지 않는다.

## 선택한 접근

기존 `ugc_reports` 신고 파이프라인에 `marketplace_trade` 원본 유형과 거래소 전용
사유를 추가한다. 새 거래 신고 테이블과 운영 화면을 만들지 않는다. 기존 파이프라인은
신고 시점 스냅샷, 처리 상태, 중복 방지, 시간당 제한, 운영 알림과 관리자 검토 흐름을
이미 제공하므로 필요한 부분만 확장하는 편이 일관되고 안전하다.

거래소 화면에는 범용 `ContentSafetyActions`를 직접 사용하지 않는다. 거래에는 사용자
차단이나 콘텐츠/사용자 선택이 맞지 않기 때문에 신고만 제공하는 거래소 전용 버튼과
대화상자를 둔다. 서버 저장과 운영 검토는 공용 신고 API를 사용한다.

고려했지만 선택하지 않은 접근은 다음과 같다.

- 별도 `marketplace_trade_reports` 테이블과 관리자 탭: 도메인 분리는 선명하지만 신고
  상태·중복 제한·운영 알림·관리 화면을 중복 구현해야 한다.
- 건의함에 거래 번호를 보내기: 구현은 작지만 권위 있는 거래 스냅샷과 당사자 정보가
  자동 보존되지 않아 조사 품질이 낮다.

## 사용자 화면

### 최상위 탭

거래소 최상위 탭을 `구매 · 판매 · 최근 거래 · 내 거래` 네 개로 구성한다. 기존
`내 거래 > 거래 내역`은 본인의 매수·매도 기록으로 유지한다.

`최근 거래` 탭은 체결 시각 내림차순으로 최신 100건을 요청하고 페이지당 10건씩
표시한다. 탭을 실제로 열었을 때만 공개 기록을 요청한다. 각 행에는 다음 정보만
노출한다.

- 아이템 이름과 현재 화면에서 이미 제공하는 장비·개체 옵션
- 거래 수량
- 총 거래가와 스택형 품목의 개당 가격
- 상대 체결 시각
- `신고` 버튼

판매자 이름, 구매자 이름, 사용자 UUID, 매수·매도 방향은 공개 응답과 화면에 넣지
않는다. 로딩 중, 빈 목록, 조회 실패 상태는 기존 거래소 목록 패턴으로 표시한다.
목록 카드와 신고 대화상자는 `Card`, `SURFACE_CARD`, `SURFACE_INSET` 등 불투명 표면을
사용해 라이트·다크 모드 모두에서 지역 배경이 본문 뒤로 비치지 않게 한다.

### 거래 신고

신고 대화상자는 다음 사유만 제공한다.

- `abnormal_price`: 비정상적으로 높거나 낮은 가격
- `market_manipulation`: 시세 조작 의심
- `real_money_trade`: 현금 거래·계정 간 자산 이전 의심
- `other`: 기타

추가 설명은 선택 사항이며 기존과 동일하게 최대 500자다. 거래 신고는 항상
`subjectType: "content"`, `sourceType: "marketplace_trade"`, `sourceId: <listing id>`로
접수한다. 사용자 차단과 신고 대상 사용자 선택은 제공하지 않는다.

접수 성공, 이미 처리 중인 중복 신고, 시간당 제한, 존재하지 않거나 체결되지 않은
거래, 네트워크 실패를 각각 이해할 수 있는 문구로 안내한다.

### 구매 화면의 본인 매물

스택형 품목 묶음은 지금처럼 다른 사용자의 고정가 매물만 포함한다. 본인의 재료·소모품
매물은 같은 검색·종류·정렬 필터를 거친 뒤 각 등록 건을 별도 `내 매물` 카드로
표시한다. 같은 품목에 다른 사용자의 매물이 있으면 구매 묶음과 본인 카드가 함께
보일 수 있다.

본인 카드에는 실제 등록 수량과 가격을 표시하고 구매 동작 대신 `내 매물 관리`
버튼을 둔다. 이 버튼은 `내 거래 > 판매 중`으로 이동한다. 본인 매물은 다음 값에
영향을 주지 않는다.

- 구매 가능한 총수량과 최저 개당 가격
- 입력 수량에 대한 자동구매 견적
- 실제 자동구매 요청에 전달하는 후보 매물

고정가 장비의 본인 카드도 동일한 관리 동선을 제공한다. 공개 입찰 중인 본인 매물의
기존 입찰 내역 확인 동작은 유지한다.

## 서버 데이터 흐름

### 최근 체결 조회

`GET /api/v2/marketplace/history`의 전체 조회와 `?mine=1` 본인 조회는 모두
`MARKETPLACE_V2_HISTORY_LIMIT = 100`을 사용한다.

전체 조회는 계속 다음 필드만 반환한다.

- `id`, `kind`, `itemId`, `itemName`, `quantity`, `price`
- `instancePayload`, `closedAt`

본인 조회만 내부적으로 판매자·구매자를 비교해 `side: "buy" | "sell"`을 파생하고,
계정 식별자 자체는 반환하지 않는다. 전체 조회의 짧은 서버 캐시는 유지하되 캐시 값에
계정 필드를 넣지 않는다. 완료 거래의 기존 60일 보관 정책은 변경하지 않는다.

### 거래 원본 해석과 신고 저장

`resolveUgcSource`가 `marketplace_trade`를 받을 때 숫자 매물 ID로
`marketplace_listings_v2`를 다시 조회한다. `status = 'sold'`이고 `closed_at`이 있는
행만 신고 원본으로 인정한다. 클라이언트가 보낸 아이템·가격·계정 정보는 신뢰하지
않는다.

신고의 `contentSnapshot`에는 아이템 이름·ID·종류, 수량, 총액, 계산 가능한 개당 가격,
체결 시각과 매물 ID를 저장한다. `contextSnapshot`에는 판매자·구매자 ID와 이름,
장비/소모품 개체 스냅샷, 입찰가·입찰 수·낙찰 시각 등 조사에 필요한 원본 거래 문맥을
저장한다. 이 값은 공개 API 응답으로 되돌려 보내지 않는다. 거래 행이 이후 보관 정책에
따라 삭제돼도 접수된 신고 스냅샷은 기존 신고 보관 정책 동안 남는다.

기존 신고 스키마가 단일 `targetUserId`를 요구하므로 운영 목록의 주 대상은 다음처럼
정한다.

- 신고자가 판매자면 구매자를 주 대상으로 삼는다.
- 신고자가 구매자면 판매자를 주 대상으로 삼는다.
- 제3자 신고면 판매자를 주 대상으로 삼는다.
- 반대편 계정이 이미 삭제돼 없으면 남아 있는 당사자를 사용한다.

양쪽 계정은 항상 가능한 범위에서 `contextSnapshot`과 운영 알림의 관련 계정 목록에
함께 넣는다. 이 규칙은 당사자가 자기 거래를 신고할 때 기존 자기 자신 신고 금지에
걸리지 않게 하면서, 관리자가 거래 전체를 조사할 수 있게 한다. 유효한 대상 계정이
하나도 남지 않은 거래는 신고할 수 없는 원본으로 처리한다.

### 검증과 제한

공용 신고 사유 타입은 기존 콘텐츠 사유와 거래 사유의 합집합을 인식한다. 범용 콘텐츠
신고 UI는 기존 콘텐츠 사유만 계속 표시하고, 거래 신고 UI는 거래 사유만 표시한다.
서버는 `marketplace_trade`에는 거래 사유와 `content` 대상만 허용해 조작된 조합을
거부한다.

DB 마이그레이션은 `ugc_reports_source_type_check`에 `marketplace_trade`를,
`ugc_reports_reason_check`에 세 신규 사유를 추가한다. `(reporter, subject, source type,
source id)` 활성 중복 인덱스와 모든 신고를 합산하는 시간당 10건 제한은 그대로
사용한다.

운영 신고 목록은 원본 유형을 `거래소 체결`로, 세 신규 사유를 합의한 한글 문구로
표시한다. 운영 알림에는 공개 UI와 달리 판매자·구매자 양쪽 계정과 거래 요약을 넣어
초기 조사에 활용한다.

## 오류 처리와 보안

- 비로그인 최근 체결 조회와 신고는 기존처럼 `401`을 반환한다.
- 숫자가 아닌 매물 ID, 활성·취소·만료 매물, 존재하지 않는 매물은 신고 원본으로
  인정하지 않는다.
- 이미 열린 동일 거래 신고는 `409`, 시간당 한도 초과는 `429`로 유지한다.
- 공개 최근 체결 응답에는 코드 수준의 회귀 테스트로 판매자·구매자 ID와 이름이 없음을
  검증한다.
- 신고 실패가 최근 체결 목록 자체를 지우지 않는다. 성공한 행은 현재 화면에서 접수
  완료 상태를 표시해 불필요한 재시도를 줄인다.
- 구매 서버는 이미 본인 매물 구매를 거부한다. UI 변경 후에도 이 서버 권위 검사를
  유지한다.

## 테스트

- 전체 최근 체결이 최신순 최대 100건이며 계정 ID·이름·방향을 반환하지 않는 API 테스트
- 본인 체결이 최대 100건이며 매수·매도 방향만 정확히 파생하는 API 테스트
- 판매 완료 거래만 신고 원본으로 해석하고 서버 권위 스냅샷을 생성하는 테스트
- 신고자 역할에 따라 반대편 당사자를 주 대상으로 선택하고 양쪽 계정을 조사 문맥에
  보존하는 테스트
- 거래 원본에 콘텐츠 신고 사유 또는 `subjectType: "user"`를 보낸 요청을 거부하는 테스트
- 거래 전용 사유 접수, 활성 중복, 시간당 제한과 운영 알림 관련 계정 테스트
- 거래 신고 대화상자의 네 사유, 500자 제한, 성공·중복·제한·원본 없음 안내 렌더 테스트
- 본인 스택 매물이 구매 화면의 개별 카드에 나타나는 회귀 테스트
- 본인 스택 매물이 구매 묶음 수량·최저가·견적에서 제외되는 테스트
- `내 매물 관리`가 `내 거래 > 판매 중`으로 이동하는 UI 테스트
- 관련 Vitest, TypeScript, ESLint와 이미지 참조 검증

## 제외 범위

- 판매자·구매자 이름 또는 익명 별칭의 공개
- 자동 의심 점수 계산, 자동 신고, 자동 제재
- 거래 신고 전용 테이블과 별도 관리자 화면
- 완료 거래 60일 보관 정책 변경
- 과거 거래 데이터 변환 또는 운영 데이터 수동 조사
- 배포와 점검 모드 변경
