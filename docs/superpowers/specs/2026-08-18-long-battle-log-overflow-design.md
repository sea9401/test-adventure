# 긴 일괄 사냥 전투 로그 전체 열람 설계

## 배경

현재 던전 일괄 사냥은 한 요청에서 최대 50회의 전투 결과를 반환한다. 응답 크기를 줄이기 위해 각 전투 로그를 마지막 80개 항목으로 제한하며, 앞부분을 제거한 경우 `앞선 턴 기록 생략 (긴 전투)` 안내를 넣는다. 제거된 로그는 서버나 클라이언트에 남지 않으므로 사용자는 해당 결과 화면에서도 앞선 턴을 확인할 수 없다.

일괄 사냥 결과는 화면을 떠난 뒤 다시 찾아 들어가는 전적 기능이 아니다. 따라서 장기 보관은 요구하지 않으며, 현재 결과 화면에서 전투 기록을 선택해 보는 동안에만 전체 로그를 제공하면 된다.

## 목표

- 일괄 사냥의 긴 전투도 첫 행동부터 마지막 행동까지 전부 열람할 수 있다.
- 최대 50회 사냥의 전체 로그를 최초 응답에 싣지 않는다.
- 전투 결과 화면과 로그 전달 기능의 유효 시간인 2시간 동안만 긴 로그를 임시 보관한다.
- 짧은 전투에는 추가 DB 쓰기나 조회를 만들지 않는다.
- 로그 저장 장애가 이미 완료된 사냥과 보상 처리를 취소하지 않게 한다.

## 제외 범위

- 결과 화면을 닫은 뒤 전투 기록 목록에서 다시 찾아가는 영구 전적 기능
- 2시간을 넘는 로그 보관
- 단판 사냥, 원정, 협동 보스, 훈련, 아레나의 로그 정책 변경
- 전투 로그 표현 형식 자체의 압축 또는 전투 재현을 위한 결정론적 시드 도입

## 선택한 방식

로그가 80개를 초과하는 일괄 사냥 전투만 기존 `battle_replays` 저장소에 전체 페이로드를 임시 저장한다. 일괄 사냥 응답에는 전체 로그 대신 기존 `replayId` 참조형 페이로드를 넣는다. 사용자가 그 회차의 `전체 전투 로그 보기`를 누르면 기존 `/api/v2/battle-replays/[replayId]` 경로로 전체 로그를 읽는다.

80개 이하인 전투는 현재처럼 로그를 응답에 직접 포함한다. 따라서 짧은 전투는 DB 저장과 후속 조회가 없다.

### 대안과 판단

1. 모든 로그를 최초 응답에 포함하면 구현은 단순하지만 50회 사냥에서 모바일 네트워크·JSON 파싱·메모리 비용이 커진다.
2. 모든 일괄 사냥 로그를 24시간 저장하던 이전 방식은 동작하지만, 짧은 전투까지 최대 50행을 쓰고 실제 열람 기간보다 오래 보관한다.
3. 배치 전체를 한 개의 압축 객체로 저장하면 저장 효율은 높지만 새 스키마와 조회 규약이 필요하다. 현재 요구에는 기존 임시 저장소를 선택적으로 쓰는 편이 작고 안전하다.

## 서버 데이터 흐름

1. 각 일괄 사냥 전투는 전체 `ReplayPayload.log`를 유지한 채 계산을 마친다.
2. 보상과 캐릭터 상태를 저장하는 핵심 트랜잭션을 먼저 완료한다.
3. 응답을 만들 때 각 전투의 로그 길이를 검사한다.
   - 80개 이하: 전체 페이로드를 그대로 응답에 포함한다.
   - 80개 초과: 전체 페이로드를 `battle_replays`에 저장하고 `replayId`와 빈 `log`를 가진 참조형 페이로드로 치환한다.
4. 임시 로그의 `expiresAt`은 생성 시각으로부터 2시간으로 설정한다.
5. 사용자가 긴 전투를 열면 기존 소유자 검증을 거쳐 전체 페이로드를 조회한다.
6. 만료된 행은 기존 운영 보존 정리 작업이 `expiresAt` 기준으로 삭제한다.

로그 임시 저장은 사냥 보상 트랜잭션의 필수 조건이 아니다. 임시 저장이 실패하면 사냥 결과를 실패시키지 않고 해당 전투의 전체 로그를 인라인으로 반환한다. 이 경우에만 응답이 커질 수 있지만, 기록 유실과 보상 롤백을 피하는 편을 우선한다.

## 코드 경계

- `replayPayload.ts`
  - 일괄 사냥용 `logCap`과 `clampReplayLog`를 제거한다.
  - 일반 변환은 항상 전체 로그를 보존한다.
  - 기존 `toDeferredReplayPayload` 참조형은 그대로 사용한다.
- `dungeon/hunt/route.ts`
  - 전투 계산 중 로그를 자르지 않는다.
  - 핵심 트랜잭션 완료 후 긴 로그만 선택해 임시 저장하고 응답을 참조형으로 바꾼다.
- `battleReplayStore.ts`
  - 보관 기간을 일 단위가 아닌 밀리초 단위 정책으로 표현해 일괄 사냥 2시간과 아레나 14일을 명확히 지원한다.
  - 긴 로그만 선택적으로 저장하는 처리는 호출부 또는 작은 전용 함수로 분리한다.
- `ReplayBattleScene.tsx`
  - `log=[]`과 `replayId` 조합을 지연 조회하는 기존 동작을 유지한다.
  - 조회할 수 없으면 `전투 기록 보관 시간이 지났거나 찾을 수 없습니다.`라고 안내하고 재시도 버튼을 제공한다.

## 오류 및 보안 처리

- 저장 실패: 사냥 성공과 보상은 유지하고 전체 로그를 인라인 응답한다.
- 조회 실패: 결과 화면을 깨뜨리지 않고 만료·부재 안내와 재시도를 표시한다.
- 접근 제어: 기존처럼 `replayId`뿐 아니라 현재 사용자 ID를 함께 조건으로 조회한다.
- 캐시: 전투 로그 조회 응답은 기존 `private, no-store` 정책을 유지한다.
- 만료: 2시간이 지나면 조회하지 못하며, 삭제 전이라도 `expiresAt` 검증으로 차단한다.

## 테스트

- 80개 이하 로그는 인라인으로 유지되고 임시 저장하지 않는다.
- 81개 이상 로그는 전체 내용으로 저장되며 응답은 `replayId`와 빈 `log`를 가진다.
- 저장된 긴 로그를 조회하면 첫 항목부터 마지막 항목까지 순서와 내용이 보존된다.
- 일괄 사냥 응답에 `앞선 턴 기록 생략 (긴 전투)` 문구가 더 이상 생성되지 않는다.
- 임시 저장 실패 시 보상 결과는 성공으로 유지되고 전체 로그가 인라인으로 반환된다.
- 다른 사용자의 `replayId`, 만료된 ID, 존재하지 않는 ID는 조회할 수 없다.
- 기존 아레나 14일 보관 정책과 지연 조회가 유지된다.
- `ReplayBattleScene`은 지연 로그 로딩, 실패 안내, 재시도를 올바르게 표시한다.

## 완료 기준

- 2회 이상 일괄 사냥에서 80개를 넘는 긴 전투 기록을 열었을 때 첫 행동부터 확인할 수 있다.
- 최초 일괄 사냥 응답에는 긴 전투 전체 로그가 중복 포함되지 않는다.
- 짧은 전투는 추가 DB 저장 없이 기존과 동일하게 표시된다.
- 로그 저장 또는 조회 장애가 사냥 보상과 결과 요약을 훼손하지 않는다.
