# 도감 숙련 B2 게임플레이 기록 연결 설계

상태: 기존 도감 숙련 엔드게임 설계의 승인된 구현 4단계
작성일: 2026-08-20
기반: `docs/superpowers/specs/2026-08-20-codex-mastery-endgame-design.md`

## 1. 목표와 범위

B2는 어보, 몬스터, 직업의 서버 권위 진행을 Phase A/B1의 중앙 기록 서비스에 연결한다.
기존 보상과 세이브 의미는 바꾸지 않고, 같은 게임 행동 트랜잭션 안에서만 숙련을 기록한다.

- 정상 챔질로 확정된 일반 낚시 어획은 해당 어종에 `amount = 1`, `bestValue = size`를 기록한다.
- 정상 사냥 승리는 현재 카탈로그의 안정적인 `enemy.key`에 실제 승리 수만 기록한다.
- 서버가 `jobCumLevel`을 올린 모든 운영 경로는 동일한 직업 ID와 실제 증가량을 기록한다.
- 온라인 단판, 온라인 일괄 사냥, 오프라인 정산은 모두 같은 영구 숙련 결과를 만든다.
- 실패, 취소, 놓친 챔질, 사냥 패배, 개발자 지급은 기록하지 않는다.
- 특별 인장, 트로피, 랭킹 UI, 월간 연구전은 B2 범위 밖이며 기능 스위치는 계속 꺼 둔다.

## 2. 접근안과 선택

### 선택안: 성공 트랜잭션 안에서 중앙 기록 서비스를 직접 호출

게임 행동이 권위 세이브를 갱신한 뒤 같은 트랜잭션에서 숙련 진행과 요약도 갱신한다. 기록 실패는
행동 전체를 롤백하므로 보상과 숙련이 갈라지지 않는다. 일괄 처리에서는 이벤트를 메모리에 모아
카테고리·항목·출처별로 합친 뒤 호출 수를 줄인다.

### 제외안: 비동기 이벤트 또는 아웃박스

게임 응답은 빨라지지만 별도 소비자, 재시도 키와 운영 복구가 필요하며 B2 범위를 크게 넓힌다.
숙련 기록 지연과 보상-기록 불일치 상태도 생긴다.

### 제외안: 매 행동 후 기존 JSON 세이브 전체 재계산

백필에는 적합하지만 실시간 경로에서는 저장 키를 다시 읽고 모든 항목을 비교해야 한다. 직접 이벤트보다
비싸고, 저장되지 않은 행동 증거를 복원할 수도 없다.

## 3. 중앙 게임플레이 어댑터

`src/lib/server/codexMasteryGameplay.ts`가 B2 호출 형식을 단일화한다.

```ts
type CodexMasteryGameplayEvent =
  | {
      category: "fish";
      entryId: FishId;
      amount: number;
      bestValue: number;
      source: "fishing.catch";
    }
  | {
      category: "monster";
      entryId: string;
      amount: number;
      source: "hunt.victory";
    }
  | {
      category: "job";
      entryId: string;
      amount: number;
      source: "job.victory" | "job.activity" | "job.training" | "job.consumable";
    };
```

`recordCodexMasteryGameplayBatch(tx, userId, events, now)`는 운영 설정을 한 번 읽는다. 기록 스위치가
꺼져 있으면 진행 테이블을 건드리지 않고 반환한다. 켜져 있으면 동일한
`category + entryId + source` 이벤트를 합산하고, `bestValue`는 최댓값을 사용해 안정적인 순서로
`recordCodexMastery`를 호출한다. 음수, 비정수, 오버플로 합계와 비정상 크기는 기존 중앙 서비스와
어댑터 양쪽에서 거부한다.

어댑터는 새 단계와 점수 변화 결과를 반환하지만 B2 화면 응답에는 추가하지 않는다. 이후 알림 묶기에서
같은 반환값을 재사용한다.

## 4. 어보 연결

`POST /api/v2/fishing/reel`의 성공 분기 끝에서 다음 두 이벤트를 한 번에 기록한다.

1. `fish`: 서버 세션에 박제된 `fishId`, `amount = 1`, `bestValue = size`.
2. `job`: 실제로 `addJobCumLevel`이 실행된 경우에만 `masteryJobId`, `amount = masteryGained`,
   `source = job.activity`.

세션 소비, 어획 판정, 기존 어보 저장과 같은 트랜잭션이므로 재전송은 기존 세션 멱등성에 의해 중복되지
않는다. 실패·만료·자동 생활 충돌은 이벤트 생성 지점에 도달하지 않는다. 거래된 표본과 위험 해역의
별도 어종은 일반 어보 항목을 올리지 않는다. 위험 해역에서 발생한 낚시 직업 숙련만 직업 이벤트로
기록한다.

## 5. 몬스터와 사냥 직업 연결

`runOneHunt`는 승리한 경우 `enemy.key`의 몬스터 이벤트를 만들고, 실제 직업 숙련 증가가 있으면 해당
직업 이벤트를 함께 만든다. `applyHuntProficiency` 결과에 `masteryJobId`를 추가해 라우트가 같은 직업
ID를 다시 추론하지 않게 한다.

- 단판은 반환 직전에 이벤트 배치를 기록한다.
- 온라인 일괄 사냥은 모든 완료 판의 이벤트를 `HuntBatchState`에 모아 기존 세이브 flush 뒤 한 번 기록한다.
- 오프라인 정산은 정산 루프의 완료 이벤트를 별도 수집기에 모아 루프 뒤 한 번 기록한다.
- 패배는 몬스터와 직업 이벤트를 만들지 않는다.
- 일괄 처리 도중 정상 중단되면 이미 완료한 판만 기록한다. 예외가 발생하면 바깥 트랜잭션이 전부 롤백된다.

## 6. 나머지 직업 숙련 경로

현재 운영 코드에서 `jobCumLevel`을 올리는 다음 경로를 모두 연결한다.

- 생활 활동: 농사 수확, 채광 타격·자동 정산, 벌목 타격·자동 정산, 요리, 일반·위험 해역 낚시
- 전투 활동: 일반·일괄·오프라인 사냥
- 훈련: 길드 훈련장 보상 수령
- 소비형 숙련: 숙련 증서와 협동 숙련 비급

생활 활동은 `job.activity`, 사냥은 `job.victory`, 길드 훈련은 `job.training`, 소비형 숙련은
`job.consumable`을 사용한다. 각 호출은 기존 `addJobCumLevel`의 동일 직업 ID와 증가량을 사용한다.
`src/app/api/admin/v2-grant`와 `src/app/api/v2/dev/grant`의 직접 지급은 플레이 활동이 아니며
운영 보상·QA 수치가 랭킹을 부풀릴 수 있으므로 연결하지 않는다.

## 7. 잠금, 오류와 운영

모든 연결은 이미 사용자 세이브를 잠근 게임 트랜잭션의 끝부분에서 실행한다. 도감 숙련 저장 순서는
기존 게임 세이브 뒤 `codex_mastery_summary`와 `codex_mastery_progress` 순서다. 백필도 세이브 뒤 숙련
행을 잠그므로 같은 사용자에서 역순 잠금을 만들지 않는다.

`recordingEnabled = false`이면 설정 조회 외에는 숙련 쓰기가 없다. `sealsEnabled = false`는 유지하고
B2는 인장 ID를 제출하지 않는다. 알 수 없는 항목이나 출처, 잘못된 증가량은 조용히 무시하지 않고
트랜잭션을 실패시킨다. 운영 전 카탈로그와 라우트 배선 테스트가 이를 차단한다.

## 8. 검증 기준

- 어댑터는 기능 스위치가 꺼졌을 때 기록하지 않는다.
- 여러 어종·몬스터·직업 이벤트가 항목별로 정확히 합쳐지고 최대 크기가 보존된다.
- 낚시 성공은 어종 1회와 실제 낚시 직업 증가만 제출하고 실패는 제출하지 않는다.
- 사냥 승리는 안정적인 몬스터 키와 실제 직업 ID를 제출하며 패배는 제출하지 않는다.
- 온라인 일괄·오프라인 정산은 완료 승리 수만큼 합산하되 항목당 한 번의 중앙 기록 호출을 사용한다.
- 모든 실제 `addJobCumLevel` 운영 경로가 같은 증가량을 제출하고 개발 지급은 제외된다.
- 기존 응답, SP, 전투 수치, 골드와 아이템 결과는 바뀌지 않는다.
- 집중 테스트, TypeScript, ESLint, 예산 검사와 프로덕션 빌드가 통과한다.
- Phase A/B 브랜치는 현재 미배포 스쿼시 브랜치에 포함되지 않는다.
