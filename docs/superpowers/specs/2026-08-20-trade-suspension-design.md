# 거래 정지 기능 설계

## 목표

관리자가 계정 전체 이용을 막지 않고도 특정 유저의 플레이어 간 경제 활동만 기간제 또는
영구적으로 제한할 수 있게 한다. 정지된 유저는 일반 게임과 거래 정보 조회를 계속할 수
있지만 자산을 다른 계정이나 길드로 이전하거나 다른 계정에서 받을 수 없다. 제재 부과
시점에 남아 있는 거래 노출도 정리하여 정지 중 자동 체결되는 우회를 막는다.

## 현재 문제

- 현재 제재는 `users.banned_until`을 사용하는 계정 전체 정지뿐이다.
- 거래소 등록·구매·입찰·구매주문과 유저 우편, 길드 경제 기능에는 공통 거래 제재
  판정이 없다.
- 계정 전체 정지를 부과해도 이미 등록된 매물과 구매주문, 최고 입찰 상태는 그대로 남아
  다른 유저나 예약 작업을 통해 체결될 수 있다.
- 관리자 제재 이력과 감사 로그는 있지만 거래만 제한하는 상태와 독립 해제를 표현하지
  못한다.

## 결정

### 1. 빠른 현재 상태와 이력을 분리한다

`users`에 다음 nullable 컬럼을 추가한다.

- `trade_suspended_until`: 거래 정지 만료 시각
- `trade_suspension_reason`: 유저에게 보여 줄 거래 정지 사유

영구 거래 정지는 기존 영구 밴과 같은 `9999-12-31T00:00:00.000Z` 센티넬을 사용한다.
현재 상태는 유저 기본 키로 조회하므로 별도 활성 상태 인덱스는 추가하지 않는다.

기존 `user_sanctions`는 거래 제재 이력에도 사용한다. `type`은 다음 값을 추가로 허용한다.

- `trade_suspend`: 기간 거래 정지와 기간 연장
- `trade_ban`: 영구 거래 정지

거래 정지 해제는 활성 거래 제재 이력에만 `lifted_at`, `lifted_by_email`을 기록한다. 계정
제재 해제는 거래 제재 이력을 건드리지 않고, 거래 제재 해제도 계정 제재 이력을 건드리지
않는다.

유저의 유효 거래 제한은 `banned_until`과 `trade_suspended_until` 중 현재 이후인 상태의
합집합이다. 따라서 계정 전체 정지와 영구 밴은 별도 거래 제재 행을 만들지 않아도 거래를
차단한다. 계정 제재가 해제되었을 때 독립 거래 제재가 남아 있으면 거래 차단은 계속된다.

### 2. 관리자 제재 API를 범위 기반으로 확장한다

기존 `/api/admin/sanctions` 응답에 계정 제재와 거래 제재 상태를 분리해 제공한다. 기존
최상위 계정 제재 필드는 호환성을 위해 유지하고, 새 `trade` 객체에는 다음을 포함한다.

- `suspended`
- `suspendedUntil`
- `reason`
- `permanent`

POST 요청은 `scope: "account" | "trade"`를 받는다. 기존 클라이언트처럼 `scope`가 없으면
`account`로 해석한다. 거래 범위에서는 `suspend`, `ban`, `extend`, `lift`만 허용하고
`warn`은 기존 계정 제재 기록에만 사용한다. 기간 정지와 연장은 양의 일수를 요구하며,
거래 정지 부과에는 빈 값이 아닌 유저 노출 사유를 요구한다.

거래 제재 변경에는 기존 `sanction` 관리자 권한을 사용한다. 감사 로그 액션은
`sanction.trade_suspend`, `sanction.trade_ban`, `sanction.trade_extend`,
`sanction.trade_lift`로 계정 제재와 구분하고 대상, 기간, 유저 노출 사유와 관리자 메모를
남긴다.

관리자 유저 상세의 기존 제재 영역 안에 계정 제재와 분리된 거래 제재 카드를 둔다.
기간 일수, 1일·3일·7일 프리셋, 영구 정지, 연장, 해제를 지원하며 현재 사유와 만료 시각,
최근 이력을 표시한다. 읽기 전용 모드와 `sanction` 권한 규칙은 기존과 동일하다. 새 카드와
중첩 영역은 `SURFACE_CARD`, `SURFACE_INSET`, `SURFACE_ACCENT`를 사용해 라이트·다크 모드
모두 불투명 표면을 유지한다.

### 3. 공통 거래 제재 경계를 둔다

서버에 거래 제재 판정과 잠금을 담당하는 공통 모듈을 둔다. 이 모듈은 다음 책임만 가진다.

- 유저의 계정 제재와 독립 거래 제재를 합쳐 현재 거래 가능 여부 계산
- 제한 사유, 만료 시각과 영구 여부를 정규화
- 거래 참여자 유저 행을 정렬된 ID 순서로 `FOR UPDATE` 잠금
- 제한 상태이면 공통 도메인 오류 반환

자산 이전을 수행하는 라우트와 서버 서비스는 `ensureUser` 이후, 자산을 읽거나 변경하기
전에 공통 경계를 통과해야 한다. 두 명 이상이 참여하는 체결은 모든 참여자의 상태를
확인한다. 이미 정지된 판매자의 남은 매물처럼 방어적으로 발견한 상대 제재 상태도 체결을
거절한다.

두 참여자가 있는 기존 거래 행에서 상대 ID가 필요하면 먼저 잠금 없는 조회로 ID만 찾고,
유저 행을 ID 오름차순으로 잠근 뒤 거래 행을 다시 `FOR UPDATE` 조회하고 상태와 소유자를
재검증한다. 관리자 제재 처리도 대상 유저 행을 먼저 잠근 뒤 거래 행을 잠근다. 이 순서를
모든 경로에서 지켜 제재 부과와 동시 거래를 직렬화하고 교착을 피한다.

### 4. 차단·허용 동작을 명시한다

거래 정지 중 다음 동작을 차단한다.

- 거래소 매물 등록, 즉시구매, 분할구매, 입찰과 가격 변경
- 재료·소비품·장비 구매주문 생성과 구매주문 대상 즉시판매
- 유저 간 우편과 선물 발송
- 길드 창고 입고·출고
- 길드 거래소의 계약 등록·수락·납품처럼 다른 구성원에게 자산이 이동하는 동작
- 예약 작업과 자동 매칭에서 정지 유저를 당사자로 하는 신규 체결

다음 동작은 허용한다.

- 거래소 매물·시세·입찰·거래 내역 조회
- 가격 알림처럼 자산을 이동하지 않는 개인 설정
- 본인 매물과 구매주문 취소
- 우편 읽기
- 거래소 반환금, 초과 입찰 반환금, 취소된 에스크로, 제재 전에 이미 끝난 거래의 정산금과
  시스템·관리자 보상 수령
- 채팅, 일반 플레이와 거래 관계가 없는 길드 활동

정지 전에 도착했더라도 아직 수령하지 않은 플레이어 발송 선물은 정지 기간에는 수령할 수
없다. 우편 수령 경로는 payload와 발신 주체를 서버에서 판정하여 반환·정산·시스템 보상만
허용한다. 정지 해제 후에는 기존 플레이어 선물을 정상 수령할 수 있다.

차단 응답은 HTTP 403과 함께 다음 계약을 사용한다.

```json
{
  "ok": false,
  "error": "trade_suspended",
  "reason": "유저 노출 사유",
  "expiresAt": "2026-08-27T00:00:00.000Z",
  "permanent": false
}
```

계정 전체 정지로 거래가 차단된 경우에도 거래 도메인 내부 판정은 같은 구조를 만들 수
있지만, 일반 유저 요청은 기존 `ensureUser`의 계정 정지 응답이 먼저 적용된다.

### 5. 제재 부과 시 활성 거래를 원자적으로 정리한다

거래 정지 부과와 계정 기간 정지·영구 밴 부과는 같은 활성 거래 정리 서비스를 호출한다.
서비스는 관리자 제재 트랜잭션 안에서 다음을 ID 오름차순으로 처리한다.

1. 대상이 판매자인 활성 매물을 취소하고 에스크로 물품을 대상에게 반환한다.
2. 해당 매물에 최고 입찰자가 있으면 입찰금을 그 입찰자에게 반환 우편으로 보낸다.
3. 대상의 활성 구매주문을 취소하고 남은 골드 에스크로를 대상에게 반환 우편으로 보낸다.
4. 대상이 다른 유저의 활성 매물에서 현재 최고 입찰자이면 입찰금을 대상에게 반환하고
   해당 매물의 `highest_bid`, `highest_bidder_id`를 비운다.

다른 유저의 매물은 취소하지 않으며 과거 공개 입찰 행과 `bid_count`도 감사 기록으로
보존한다. 이전 입찰자는 이미 환불되었으므로 자동으로 차순위 입찰자로 복원하지 않는다.
매물은 최고 입찰자 없는 활성 상태로 남아 새 입찰을 받을 수 있다.

현재 최고 입찰자 역조회가 제재 처리의 정상 경로가 되므로
`marketplace_listings_v2.highest_bidder_id`에 활성 매물 부분 인덱스를 추가한다. 판매 매물과
구매주문은 기존 판매자·구매자 상태 인덱스를 사용한다.

매물 물품 반환, 입찰금 반환, 구매주문 환불 로직은 기존 취소·만료 경로에서 트랜잭션을
받는 도메인 헬퍼로 추출해 재사용한다. 제재 라우트에 장비·재료·소비품 복원 로직을
복제하지 않는다. 정리 중 하나라도 실패하면 제재 상태와 모든 정리를 함께 롤백한다.
경제 이벤트는 커밋된 정리 건만 기록하고 관리자 감사 로그에는 정리한 매물·구매주문·입찰
수를 남긴다.

정지 해제는 취소된 매물, 주문이나 입찰을 자동 복구하지 않는다. 유저가 해제 후 직접 다시
등록해야 한다.

### 6. 유저 상태 안내를 확장한다

`/api/v2/me/sanctions`는 계정 제재 안내와 별도로 `tradeSuspension`을 반환한다. 여기에는
최신 활성 거래 제재 행 ID, 사유, 만료 시각, 영구 여부와 확인 여부를 포함한다. 계정 전체
정지만 있고 독립 거래 제재가 없으면 기존 계정 정지 화면이 우선하므로 별도 거래 제재
안내를 중복 표시하지 않는다.

확인하지 않은 독립 거래 제재는 `PlayerSanctionGate`에서 일반 게임을 가리지 않는 확인
모달로 한 번 안내한다. POST 확인 요청은 거래 제재 행 ID를 받아 현재 유저 소유의 활성
`trade_suspend` 또는 `trade_ban` 행에만 `acknowledged_at`을 기록한다. 확인은 차단을
해제하지 않는다. 연장은 새 이력 행을 만들기 때문에 이미 과거 제재를 확인했어도 새 기간과
사유를 다시 안내한다.

거래 화면은 403 `trade_suspended`를 공통 오류로 해석해 동일한 안내를 표시한다. 버튼을
클라이언트에서 미리 비활성화할 수 있지만 서버 판정을 보안 경계로 유지한다. 조회 화면과
취소·허용된 우편 수령 버튼은 정지 중에도 사용할 수 있게 한다.

## 구현 대상 경계

구현 계획에서 현재 라우트와 서비스의 전체 목록을 다시 생성하고 다음 범주마다 공통 제재
경계가 연결됐는지 체크한다.

- `/api/v2/marketplace`: 등록, 구매, 분할구매, 입찰, 가격 변경, 구매주문 생성, 주문 대상
  판매와 자동 매칭
- `/api/inbox/send`: 유저 메시지·선물 발송
- `/api/marketplace/inbox/claim`: 허용된 반환·정산·시스템 보상과 차단된 플레이어 선물 분기
- `/api/v2/guild/warehouse`: 입출고
- `/api/v2/guild/trade-post`: 구성원 간 자산 이동
- 거래소 만료·입찰 낙찰·구매주문 체결 예약 작업과 공용 정산 서비스

관리자 우편, 시스템 보상 생성, 운영자 지급은 플레이어 간 거래가 아니므로 발송을 막지
않는다. 거래 채팅 채널, 길드 가입·탈퇴·권한 변경과 시설 기부처럼 이번에 합의하지 않은
비거래 동작도 범위에 포함하지 않는다.

## 테스트

### 상태와 관리자 API

- 만료 전·정확한 만료 시각·만료 후와 영구 센티넬을 판정한다.
- 계정 제재와 독립 거래 제재의 합집합을 계산한다.
- 거래 정지, 영구 정지, 연장과 독립 해제가 올바른 이력만 변경한다.
- `scope`가 없는 기존 요청은 계정 제재로 동작한다.
- 거래 제재는 `sanction` 권한, 양의 기간과 유저 노출 사유를 요구한다.
- 감사 로그가 거래 제재 액션, 사유, 관리자 메모와 정리 건수를 남긴다.

### 활성 거래 정리

- 장비·재료·소비품 매물이 취소되고 동일 가치가 대상에게 반환된다.
- 판매 매물의 최고 입찰자에게 에스크로 전액이 한 번만 반환된다.
- 활성 구매주문의 잔여 에스크로가 한 번만 반환된다.
- 다른 매물의 대상 최고 입찰은 반환·초기화되고 매물과 과거 입찰 이력은 유지된다.
- 재실행은 추가 반환을 만들지 않는 멱등성을 가진다.
- 중간 실패 시 제재 상태, 매물, 주문과 반환 우편이 모두 롤백된다.

### 거래 경계와 동시성

- 모든 거래 쓰기 범주의 대표 라우트가 정지 유저를 `trade_suspended`로 거절한다.
- 구매·자동 매칭은 행위자뿐 아니라 상대 판매자·구매자 상태도 확인한다.
- 조회, 취소, 가격 알림과 허용된 우편 수령은 정지 중에도 성공한다.
- 플레이어 선물 수령은 정지 중 거절되고 해제 후 성공한다.
- 동시에 시작한 제재와 등록·구매·입찰 요청은 유저 잠금에서 직렬화되며 제재 응답이
  완료된 뒤 활성 거래 노출이 남지 않는다.
- 다중 참여자 잠금은 입력 순서와 관계없이 같은 ID 순서를 사용한다.

### UI와 회귀

- 관리자 화면에서 계정 제재와 거래 제재 상태·버튼·이력이 독립적으로 표시된다.
- 보기 전용과 권한 없는 관리자는 거래 제재를 변경할 수 없다.
- 유저 안내에 사유, 기간과 영구 여부가 표시된다.
- 거래 제재 확인은 해당 이력 행만 갱신하며 제한을 해제하지 않고, 연장 시 다시 안내된다.
- 거래 화면은 공통 403을 일관되게 안내하면서 조회·취소 기능은 유지한다.
- 기존 계정 경고·정지·영구 밴·연장·해제와 거래소 정상 체결이 회귀하지 않는다.
- 라이트·다크 모드에서 관리자 제재 카드 본문 뒤로 배경 이미지가 비치지 않는다.

## 범위 밖

- 자동 이상 거래 탐지와 자동 제재
- 거래 정지 계정의 과거 완료 거래 취소 또는 회수
- 제재 계정과 연관된 다른 계정의 연쇄 제재
- 거래 정지 중 채팅 채널 이용 제한
- 취소된 매물·주문·입찰의 자동 복구
- 길드 시설 기부와 일반 길드 활동 제한
- 운영 배포, 점검 모드 전환과 실제 유저 제재 적용
