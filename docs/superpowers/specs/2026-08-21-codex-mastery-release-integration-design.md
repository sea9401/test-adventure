# 도감 숙련도 출시 후보 재통합 설계

상태: 사용자 승인
작성일: 2026-08-21
기준 브랜치: `origin/main`
출처 브랜치:

- `hold/codex-mastery-phase-a-20260820` (`fea3aa2ee`)
- `feat/codex-mastery-gameplay-integration-20260820` (`ad43a86b2`)

## 1. 목적

운영에 보류된 도감 숙련도 전체 구현을 최신 `origin/main` 위에 도감 전용 출시 후보로 재구성한다.
Phase A 기반부터 영구 랭킹, 트로피, 숙소 전시, 월간 연구, 결산, 명예의 전당까지 하나의 의존
계층으로 복구하되 다른 세션에서 진행 중인 누락·회귀 복구 작업은 포함하지 않는다.

출시 후보는 모든 도감 기능 플래그가 기본적으로 꺼진 비활성 상태여야 한다. 이 작업은 로컬 통합과
검증까지만 수행하며 운영 배포, 운영 DB 백필, 시즌 예약, 기능 활성화와 점검 모드 변경은 포함하지
않는다.

## 2. 선택한 통합 방식

최종 브랜치 전체를 병합하거나 스쿼시하지 않고 도감 관련 커밋만 원래 의존 순서대로 선별
재적용한다.

이 방식을 선택한 이유는 공통 기준점 `81813a2a1` 이후 최종 브랜치에 196개 커밋이 있고 최신
`origin/main`과의 전체 비교가 454개 파일에 걸쳐 있기 때문이다. 전체 병합은 도감과 관계없는
미배포 작업을 다시 끌어들일 수 있다. 완성된 파일만 복사하는 방식은 공용 API, 프로필, 숙소,
랭킹과 게임플레이 경로에 들어간 작은 연결 지점을 빠뜨릴 위험이 크다.

선별 재적용은 다음 원칙을 따른다.

1. Phase A에서는 `0d1e66f55` 설계와 `69ad0c7b5` 계획을 포함한 도감 전용 커밋만 고른다.
2. `2dea39ae8`부터 `fea3aa2ee`까지의 기반 구현·수정·테스트를 의존 순서대로 적용한다.
3. `f7b20a57e`부터 `ad43a86b2`까지의 후속 도감 통합 계층을 순서대로 적용한다.
4. 커밋 제목만 믿지 않고 변경 경로와 코드 내용을 확인해 도감 범위를 판정한다.
5. 다른 기능이 섞인 커밋은 커밋 전체를 적용하지 않고 도감 관련 변경만 재구성한다.

## 3. 통합 계층

재적용과 검증은 다음 경계로 나눈다.

1. 도메인 엔진, 카탈로그 검증, 저장소, 트랜잭션 기록, 요약 복구와 운영 스위치
2. 운영 카탈로그, 과거 기록 백필과 절대 목표 동기화
3. 낚시, 사냥, 생활, 요리, 장비, 직업 활동의 서버 권위 기록 연결
4. 모험의 서 숙련 개요, 항목 목록, 진행도와 고정 목표 UI
5. 영구 종합·분야별 랭킹
6. 성장형 도감 트로피, 프로필 전시대와 트로피 연혁
7. 개인 숙소의 도감 트로피 전시
8. 개인 월간 연구 진행과 현재 시즌 UI
9. 월간 랭킹 결산과 월간 트로피
10. 운영 미리보기·예약·결산·발급 도구
11. 확정 기록 공개, 개인 알림, 전광판과 명예의 전당

각 계층의 집중 테스트가 통과한 뒤 다음 계층으로 넘어간다. 중간 계층에서 문제가 생기면 이후
계층을 먼저 적용해 우회하지 않는다.

## 4. 충돌과 범위 관리

충돌은 최신 `main`의 현재 동작을 기준으로 해결한다. 출처 브랜치의 파일 전체로 덮어쓰지 않고 해당
도감 계약만 옮긴다. 특히 다음 공용 표면은 도감 외 변경이 유입되지 않았는지 별도로 감사한다.

- 게임플레이 보상·드롭·생활 활동 경로
- 운영 설정과 관리자 API
- 모험의 서와 랭킹 내비게이션
- 프로필 대표 전시와 개인 숙소 저장 모델
- 알림·전광판
- DB 스키마와 마이그레이션 저널

충돌 해결이 기존 동작을 바꾸면 회귀 테스트를 먼저 추가한다. 설치된 Next.js 버전의 경로나
컴포넌트 코드를 수정할 때는 `node_modules/next/dist/docs/`의 관련 문서를 먼저 확인한다.

출처 구현이 다른 미배포 기능을 전제로 한다면 그 기능을 함께 가져오지 않는다. 도감 쪽에 좁은
호환 계층을 만들 수 있으면 테스트와 함께 추가하고, 그렇지 않으면 해당 의존성을 통합 보고서에
명시해 출시 후보 완료를 보류한다.

## 5. 데이터와 비활성 배포 경계

출처 브랜치의 도감 마이그레이션은 `0169`부터 `0173`이었지만 최신 `main`이 `0169`와 `0170`을
이미 사용한다. SQL 의미와 상대 순서를 유지하면서 출시 후보에서는 `0171`부터 `0175`로 재번호화한다.

- `0171_codex_mastery_foundation.sql`
- `0172_codex_mastery_trophy_history.sql`
- `0173_wandering_scrambler.sql`
- `0174_codex_research_settlement.sql`
- `0175_codex_research_publication.sql`

마이그레이션은 새 PostgreSQL과 현재 운영 마이그레이션 계보를 반영한 검증 DB에서 모두 실행한다.
기존 종료 시즌을 자동 공개하거나 자동으로 트로피를 발급하는 데이터 변경은 허용하지 않는다.

`codex-mastery-features.v1`의 다음 아홉 스위치는 출시 후보에서 모두 `false`가 기본값이다.

```text
recordingEnabled, overviewVisible, rankingVisible, sealsEnabled,
trophiesEnabled, monthlyProgressEnabled, monthlyRankingVisible,
settlementEnabled, feedEnabled
```

도감 전용 운영 cron과 실제 운영 시즌 정의는 포함하지 않는다. 예약, 결산, 발급과 공개는 정확한
확인 문자열을 요구하는 수동 운영 작업으로 남긴다.

## 6. 과거 기록 백필과 실제 전환

로컬 출시 후보 검증에서는 백필을 일회용 PostgreSQL 데이터로만 시험한다. 향후 운영 적용은 별도
승인을 받은 점검 상태에서 다음 순서로 수행한다.

1. DB 백업과 복구 지점을 확인한다.
2. 모든 도감 기능 스위치가 꺼져 있는지 확인한다.
3. 백필 dry-run으로 대상 사용자 수와 예상 변경량을 기록한다.
4. 내부 표본 계정에 적용하고 원본 저장값, 진행 이벤트와 요약을 대조한다.
5. 전체 백필을 적용한다.
6. 같은 백필을 다시 dry-run해 변경 예정이 0건인지 확인한다.
7. 요약 복구와 트로피 재구축도 각각 dry-run 후 적용하고 멱등성을 확인한다.
8. 사용자 활동이 재개되기 전에 `recordingEnabled`를 켠다.

백필 완료와 기록 활성화 사이에는 사용자 활동을 허용하지 않는다. 그래야 이미 처리된 사용자의
레거시 카운터가 증가했지만 새 도감 이벤트에는 기록되지 않는 공백을 막을 수 있다. 운영 배포와
점검 해제는 각각 별도 사용자 승인 없이는 수행하지 않는다.

## 7. 단계별 공개

비활성 코드와 스키마의 운영 반영이 별도로 승인되고 데이터 전환까지 끝난 뒤 다음 순서로 기능을
연다.

1. 영구 도감 기록 수집
2. 개인 숙련 개요
3. 영구 종합·분야별 랭킹
4. 인장·성장형 트로피·프로필과 숙소 전시
5. 월간 연구 진행 기록
6. 월간 랭킹을 닫은 내부 시험 시즌
7. 결산 미리보기, 확정 결산과 트로피 발급
8. 월간 공개 랭킹, 개인 알림과 명예의 전당
9. 별도 승인 뒤 다이아·전설 전체 소식과 전광판

각 단계에서 오류율, 응답 시간, 기록 증가량, 순위 일관성과 사용자 문의를 확인한다. 한 단계에서
이상이 생기면 관련 표시 플래그를 끄고 권위 데이터는 삭제하거나 직접 수정하지 않는다.

## 8. 검증과 완료 조건

재통합 출시 후보는 다음 검증을 새로 통과해야 한다.

- 도감 도메인, 기록 연결, UI, 랭킹, 트로피, 숙소, 월간 연구와 운영 도구 집중 테스트
- PostgreSQL 기반 백필, 영구 랭킹, 월간 결산과 공개 통합 테스트
- `npm run check-migrations`
- `npm run check-images`
- `npm run check:codex-mastery-release`
- TypeScript 타입 검사와 관련 파일 ESLint
- 프로덕션 빌드
- 전체 테스트 1회

출시 후보와 출처 브랜치를 다음 두 방향으로 대조한다.

1. 출처의 도감 전용 파일과 공용 파일의 도감 관련 코드가 출시 후보에 모두 존재하는지 확인한다.
2. 출시 후보의 변경 중 도감 범위로 설명할 수 없는 파일이나 코드가 없는지 확인한다.

검증 중 실패가 발생하면 원인을 확인하고 회귀 테스트를 먼저 추가한 뒤 최소 변경으로 수정한다.
타임아웃이나 기존 실패를 도감 성공으로 간주하지 않으며, 도감과 무관한 기존 실패는 재현 증거와
영향 분석을 분리해 보고한다.

완료 상태는 모든 기능이 기본 OFF인 깨끗한 로컬 도감 전용 커밋과 검증 기록이다. 이 상태만으로
푸시, PR, 배포, 운영 DB 변경이나 기능 활성화를 수행하지 않는다.
