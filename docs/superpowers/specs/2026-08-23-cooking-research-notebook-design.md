# 요리 연구 기록과 중복 시도 방지 설계

## 목표

요리의 숨은 조합을 직접 찾는 구조는 유지하면서, 이미 시도한 오답을 게임 안에서 확인하고 같은 실패를 반복하기 전에 알아볼 수 있게 한다.

## 범위

- 연구 화면에 최근 실패 조합을 최대 100개까지 최신순으로 표시한다.
- 각 기록에는 조리법, 선택했던 재료, 시도 시각을 표시한다.
- 현재 선택한 조리법과 재료가 실패 기록에 있으면 연구 버튼을 비활성화하고 재료가 소비되지 않는다는 안내를 표시한다.
- 성공한 조합은 기존 요리 도감에서 계속 확인한다.
- 실패 이유, 정답 재료, 유사도, 재료나 양념의 방향성은 공개하지 않는다.

## 데이터와 API

기존 `cooking_failed_combinations` 테이블이 `method`, `ingredient_ids`, `created_at`을 이미 저장하므로 새 테이블이나 마이그레이션을 만들지 않는다. `/api/v2/cooking`의 GET 및 mutation 후 응답에 현재 사용자의 최근 기록을 다음 형태로 추가한다.

```ts
type CookingFailedResearchView = {
  method: CookingMethod;
  ingredientIds: CookingIngredientId[];
  createdAt: number;
};
```

서버는 `user_id`로 제한하고 `created_at DESC`로 정렬한 뒤 100개만 반환한다. 조합 해시는 클라이언트에 보낼 필요가 없다. 기존 POST의 권위 검증과 `duplicate_combination` 방어는 그대로 유지하므로, 응답 범위 밖의 오래된 기록이나 여러 탭 경쟁에서도 재료가 중복 소비되지 않는다.

## UI와 동작

`CookingResearchPanel`은 실패 기록을 현재 응답과 함께 받는다. 연구 선택의 비교 키는 조리법과 정렬한 재료 ID로만 만들며, 서버의 비밀 레시피 카탈로그나 해시 구현을 클라이언트로 옮기지 않는다.

연구 재료 선택 영역 아래에 불투명 `SURFACE_INSET` 연구 기록을 둔다. 기록이 없으면 첫 시도를 권하는 빈 상태를 표시하고, 기록이 있으면 각 항목을 불투명 `SURFACE_CARD` 행으로 보여 준다. 성공 기록은 중복 표시하지 않고 기존 도감으로 안내한다.

선택 조합이 최근 실패 기록과 같으면 버튼을 비활성화하고 `이미 실패한 조합 · 재료는 소비되지 않습니다`를 표시한다. 기록을 불러오지 못했거나 100개 범위 밖의 오답이면 기존 서버 응답이 최종 방어선이다.

## 접근성과 표면

- 기록은 제목과 목록 구조로 제공한다.
- 중복 선택 안내는 `role="status"`로 변경을 알린다.
- 잠긴 상태는 카드 전체 투명도가 아니라 버튼 비활성화와 텍스트 색으로 표현한다.
- 모든 중첩 패널은 `SURFACE_CARD` 또는 `SURFACE_INSET`을 사용해 라이트·다크 모드에서 배경이 비치지 않게 한다.

## 오류 처리와 보안

- DB의 조리법과 재료 ID는 알려진 공개 식별자만 응답에 포함한다.
- 미발견 레시피 조합이나 정답 후보는 응답에 포함하지 않는다.
- 클라이언트의 사전 경고와 관계없이 서버는 기존 조합 해시 검사를 계속 수행한다.
- 조회 결과가 비어도 연구 기능은 정상 동작한다.

## 테스트

- GET이 현재 사용자의 실패 기록을 최신 응답에 포함하는지 검증한다.
- 실패 연구 직후 응답에도 새 기록이 포함되는지 검증한다.
- 기록 목록이 조리법과 재료명을 표시하는지 검증한다.
- 이미 실패한 조합을 다시 선택하면 연구 버튼이 잠기고 mutation이 호출되지 않는지 검증한다.
- 기록이 없어도 기존 연구 동작이 유지되는지 검증한다.

## 제외 범위

- 재료 수급량과 밭 개수 조정
- 레시피 추가
- 사냥·낚시·실패 결과에서 정답 방향을 주는 힌트
- 실패 기록 검색, 서버 페이지네이션, 전체 기록 내보내기
- 배포
