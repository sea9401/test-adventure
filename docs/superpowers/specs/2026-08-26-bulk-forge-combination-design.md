# 대장간 일괄 조합 설계

## 목표

대장간의 조합 탭에서 같은 레시피를 여러 번 누르지 않고 원하는 수량을 한 번에 조합한다. 기존 1개 조합은 그대로 지원하고, 재료·골드·희귀 지도 보유 한도를 넘는 요청은 아무것도 소비하지 않은 채 거절한다.

## 선택한 접근

각 레시피 카드에 수량 조절기(`−`, 숫자 입력, `+`, `최대`)를 추가하고, API 요청 한 번에 선택 수량을 전달한다. 서버는 총비용을 먼저 검증한 뒤 기존 트랜잭션 안에서 재료 차감과 산출물 지급을 원자적으로 처리한다.

검토한 대안은 다음과 같다.

- 클라이언트가 기존 1개 조합 API를 반복 호출: 구현은 작지만 요청 제한에 걸릴 수 있고 중간 실패 시 일부만 조합된다.
- `전부 조합` 단일 버튼: 단순하지만 재료를 일부 남기고 싶은 사용자의 선택권이 없다.

## UI와 데이터 흐름

- 레시피별 선택 수량은 클라이언트 상태로 독립 관리하며 기본값은 1이다.
- 수량 입력은 양의 정수로 정규화한다. `최대`는 현재 재료와 결제 가능 골드로 계산한 최대 수량을 선택한다.
- 선택 수량에 맞춰 카드의 필요 재료, 총 조합비, 조합 버튼 문구를 갱신한다.
- 요청 본문에 `quantity`를 담는다. 기존 호출처럼 수량을 생략하면 1개로 처리하여 호환성을 유지한다.
- 성공 알림에는 소비한 총 재료, 획득한 총 산출물, 총 골드를 표시한다.
- 희귀 지도 일괄 조합은 같은 선택 단계로 여러 장을 만들며 각 장의 종류는 독립적으로 추첨한다.

## 서버 검증과 오류 처리

- `quantity`는 생략 또는 1 이상의 안전한 정수만 허용한다. 그 외 값은 `invalid_quantity`로 거절한다.
- 재료 필요량과 골드 비용은 단위 비용에 수량을 곱해 계산하고, 저장값을 바꾸기 전에 충분한지 확인한다.
- 희귀 지도는 현재 활성 지도 수와 요청 수량의 합이 보유 한도를 넘으면 `rare_map_full`로 전체 요청을 거절한다.
- 성공 응답은 실제 조합 수량과 총 골드 비용을 반환한다.
- 모든 검증과 변경은 기존 행 잠금 및 트랜잭션 경계 안에서 처리한다.

## 테스트

- 스태미나 회복약과 수집 재료 조합 라우트에 수량 2 이상의 재료·골드 차감 및 산출물 지급 회귀 테스트를 먼저 추가한다.
- 잘못된 수량과 희귀 지도 한도 초과가 저장값을 바꾸지 않는지 검증한다.
- 수량별 총비용과 UI 최대 수량 계산을 순수 함수로 분리해 경계값을 단위 테스트한다.
- 관련 Vitest, ESLint, TypeScript 검사와 Next.js 빌드를 실행한다.

## 범위

현재 비활성화된 재련석 조합도 같은 API 계약과 UI 모델을 따르도록 준비하되, 기능 플래그를 켜지는 않는다. 강화·재련·일반 제작 시스템의 동작과 밸런스 수치는 변경하지 않는다.
