# 관리자 채팅 모니터링 설계

## 목표

최고 관리자가 전체·거래·길드·사용자 공개/비공개 채팅방의 현재 보존 중인 대화를 관리자 페이지에서 읽을 수 있게 한다. 관리자는 어떤 방에도 참여자로 등록되지 않으며, 일반 사용자에게 보이는 참여자 명단·인원수·초대 상태·방장 승계에 영향을 주지 않는다.

## 범위

- `super` 역할 관리자만 채팅 모니터링 화면과 API를 사용할 수 있다.
- 전체 채팅, 거래 채팅, 모든 활성 길드 채팅, 모든 사용자 공개/비공개 채팅방을 조회한다.
- 사용자 채팅방은 방 이름, 공개 여부, 방장, 실제 참여자 수와 참여자 명단을 함께 확인할 수 있다.
- 길드 채팅은 길드명과 길드 ID를 함께 표시한다.
- 메시지 작성, 방 입장, 초대, 강퇴, 삭제, 제재 같은 변경 기능은 제공하지 않는다.
- 메시지 보존 기간은 기존 `CHAT_RETENTION_DAYS` 정책을 그대로 따른다. 현재 정책상 관리자가 볼 수 있는 기록도 최근 3일 이내로 한정된다.
- 채팅 데이터의 보존 기간을 늘리거나 별도 사본을 만드는 기능은 포함하지 않는다.

## 선택한 접근

일반 사용자 채팅 API에 관리자 우회를 추가하지 않고 관리자 전용 읽기 API와 관리자 탭을 만든다. 관리자 조회는 `chat_room_members`나 `guild_members`를 권한 근거로 사용하지 않고 `requireAdminRole("super")`만 통과한 뒤 원본 메시지 범위를 직접 조회한다.

이 구조는 일반 채팅의 참여자 권한 경계를 유지하고, 관리자 특수 권한이 사용자 화면으로 새는 위험을 줄인다. 숨겨진 관리자 멤버십 레코드는 만들지 않으므로 방 정원, 참여 방 개수 제한, 인원수, 방장 승계, 나가기 및 차단 처리도 변하지 않는다.

## 관리자 API

### 조회 대상 목록

`GET /api/admin/chat-monitor/rooms`는 `super` 권한을 확인하고 조회 가능한 채팅 대상을 반환한다.

지원 쿼리:

- `kind`: `all | global | trade | guild | room`, 기본값 `all`
- `visibility`: 사용자방 필터인 `all | public | private`, 기본값 `all`
- `q`: 길드명, 사용자방 이름 또는 숫자 ID 검색
- `offset`: 0 이상의 정수, 기본값 `0`
- `limit`: 1~100, 기본값 `50`

응답의 각 대상은 공통 식별자인 `targetKey`를 가진다.

```ts
type AdminChatTarget =
  | {
      targetKey: "global" | "trade";
      kind: "global" | "trade";
      label: string;
      latestMessageAt: string | null;
    }
  | {
      targetKey: `guild:${number}`;
      kind: "guild";
      scopeId: number;
      label: string;
      latestMessageAt: string | null;
    }
  | {
      targetKey: `room:${number}`;
      kind: "room";
      scopeId: number;
      label: string;
      visibility: "public" | "private";
      ownerId: string;
      ownerName: string;
      memberCount: number;
      latestMessageAt: string | null;
    };
```

전체·거래 대상은 첫 페이지에만 한 번 포함한다. 길드와 사용자방은 최근 메시지 시각을 우선하고, 메시지가 없으면 생성 시각을 사용해 최신 활동순으로 정렬한다. `total`과 다음 페이지 존재 여부인 `hasMore`를 함께 반환한다. 해산된 길드는 목록에서 제외한다. 사용자방은 메시지가 없어도 목록에 포함한다.

### 메시지와 선택 대상 상세

`GET /api/admin/chat-monitor/messages`는 다음 쿼리를 받는다.

- `kind`: `global | trade | guild | room`
- `scopeId`: `guild`와 `room`일 때 필요한 양의 정수
- `beforeId`: 이전 메시지를 가져올 때 사용하는 양의 메시지 ID
- `limit`: 1~100, 기본값 `100`

조회 조건은 일반 채팅과 같은 범위를 사용한다.

- `global`: `channel = global`, `guildId`와 `roomId` 모두 `NULL`
- `trade`: `channel = trade`, `guildId`와 `roomId` 모두 `NULL`
- `guild`: `channel = guild`, 요청한 `guildId`, `roomId = NULL`
- `room`: `channel = room`, 요청한 `roomId`, `guildId = NULL`

최초 조회는 최신 메시지부터 최대 100개를 ID 내림차순으로 반환한다. `beforeId` 조회는 같은 대상 안에서 그보다 작은 ID만 반환한다. 응답은 `hasMore`와 다음 요청에 쓸 `nextBeforeId`를 함께 제공한다. 각 메시지는 메시지 ID, 작성자 사용자 ID, 전송 당시 이름·직업·칭호, 본문, 장비 링크, 전송 시각을 포함한다. 관리자 개인 차단 목록은 적용하지 않는다.

선택 대상의 존재를 먼저 확인한다. 없는 길드나 사용자방은 `404`를 반환한다. 사용자방 최초 응답에는 실제 참여자를 방장 우선, 참여 시각순으로 정렬해 포함한다. 이 명단은 `chat_room_members` 원본만 사용하므로 관리자 계정은 포함되지 않는다. 길드 최초 응답에는 길드 기본 정보만 포함하고 길드 참여자 전체 명단은 이번 범위에서 제외한다.

두 관리자 API 모두 데이터를 읽기만 하며 채팅, 멤버십, 초대, 저장 데이터에 쓰기 쿼리를 실행하지 않는다.

## 권한과 감사 로그

각 라우트 내부에서 `requireAdminRole("super")`를 호출한다. 로그인하지 않은 요청은 `401`, 관리자 외 요청과 하위 관리자 역할은 `403`을 반환한다. 클라이언트 화면에서 탭을 숨기는 것은 보조 수단일 뿐 권한 판단으로 사용하지 않는다.

메시지 API의 모든 성공 응답은 빈 결과를 포함해 `logAdminAction`으로 `chat_monitor.read` 감사 로그를 남긴다. 로그 상세에는 `kind`, `scopeId`, `beforeId`, 반환된 메시지 수를 기록하며 메시지 본문은 기록하지 않는다. 관리자 이메일은 `currentAdminEmail()`로 결정한다. 자동 폴링을 제공하지 않아 조회 부하와 감사 로그 중복을 제한한다.

## 관리자 화면

`AdminShell`의 `소통과 운영` 그룹에 `채팅 모니터링` 탭을 추가하고 동적 로딩한다. 메뉴 항목은 `adminMe.capabilities.super`가 참일 때만 표시한다. 직접 URL로 접근하더라도 API가 다시 최고 관리자 권한을 검사하며, 권한 거절 시 화면은 민감한 메타데이터를 남기지 않는 오류 상태를 표시한다.

화면 상단에는 `최고 관리자 전용 · 읽기 전용 · 최근 3일` 안내를 표시한다. 본문은 데스크톱에서 방 목록과 메시지 상세를 나란히, 좁은 화면에서 위아래로 배치한다.

방 목록에는 종류, 이름, ID, 공개 여부, 참여 인원과 최근 활동 시각을 표시한다. 종류·공개 여부 필터, 이름/ID 검색, 새로고침과 페이지 이동을 제공한다. 방을 선택하기 전에는 안내 빈 상태를 보여준다.

메시지 상세에는 선택 대상 정보, 사용자방 참여자 명단, 수동 새로고침, `이전 메시지 더 보기`를 제공한다. 메시지는 작성자명과 사용자 ID, 전송 시각, 본문과 기존 서버 검증 장비 링크를 표시한다. 작성자명과 참여자명은 관리자 유저 검색으로 이동할 수 있다. 작성·입장·초대·삭제 컨트롤은 렌더링하지 않는다.

최상위 패널과 중첩 영역에는 `SURFACE_CARD`와 `SURFACE_INSET`을 사용한다. 라이트·다크 모드 모두 불투명 배경을 유지하며 컨테이너 전체 `opacity-*`나 임의의 반투명 배경을 사용하지 않는다.

## 상태와 오류 처리

- 잘못된 `kind`, 범위를 벗어난 `limit`·`offset`, 누락되거나 잘못된 `scopeId`·`beforeId`는 `400`을 반환한다.
- 삭제되었거나 해산된 선택 대상은 `404`를 반환한다.
- 목록과 메시지 조회 상태는 별도로 관리해 한쪽의 실패가 다른 쪽의 이미 로드된 데이터를 지우지 않게 한다.
- 새 대상을 선택하면 이전 대상의 메시지·참여자·페이지 커서를 즉시 초기화해 데이터가 섞이지 않게 한다.
- 이전 메시지 추가 조회 실패 시 기존 메시지를 유지하고 해당 버튼에서 재시도할 수 있게 한다.
- 보존된 메시지가 없는 경우 오류 대신 `보존 중인 메시지가 없습니다` 빈 상태를 표시한다.

## 테스트

API 테스트:

- 비로그인 요청은 `401`, 일반 사용자와 하위 관리자 요청은 `403`, 최고 관리자는 성공한다.
- 최고 관리자가 멤버가 아닌 비공개 사용자방과 가입하지 않은 길드방 메시지를 조회할 수 있다.
- 전체·거래·길드·사용자방 조건이 서로의 메시지를 포함하지 않는다.
- `beforeId` 페이지 경계에서 중복이나 다른 대상 메시지가 섞이지 않는다.
- 공개/비공개 사용자방, 빈 방과 활성 길드가 목록 필터 및 정렬 규칙에 맞게 반환된다.
- 사용자방 참여자 명단과 인원수는 실제 멤버만 포함하고 관리자 계정은 포함하지 않는다.
- 성공적인 메시지 조회가 본문 없이 `chat_monitor.read` 감사 로그를 남긴다.
- 관리자 조회 코드가 `chat_room_members` 등 도메인 테이블에 쓰기 작업을 하지 않는다.
- 기존 일반 채팅 API는 비참여자의 사용자방 조회와 비길드원의 길드방 조회를 계속 거절한다.

UI 테스트:

- 최고 관리자 전용·읽기 전용·보존 기간 안내와 필터를 렌더링한다.
- 대상 변경 시 이전 메시지가 사라지고 새 대상의 메시지만 표시된다.
- 사용자방 참여자 명단에 관리자 계정이 나타나지 않는다.
- 빈 상태, 권한 오류, 일반 조회 오류와 이전 메시지 재시도를 구분해 표시한다.
- `이전 메시지 더 보기`가 기존 메시지를 유지하면서 중복 없이 추가한다.
- 화면에 메시지 작성·입장·초대·삭제 컨트롤이 없다.

완료 전 관련 테스트, ESLint, TypeScript 검사와 프로덕션 빌드를 실행한다. 구현 전 현재 저장소의 `node_modules/next/dist/docs/`에서 관리자 페이지와 Route Handler에 해당하는 Next.js 문서를 확인하고 현재 버전 규칙을 따른다.
