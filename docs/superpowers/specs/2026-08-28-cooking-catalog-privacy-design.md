# 요리 카탈로그 비공개 경계 설계

## 목표

브라우저 개발자 도구의 API 응답과 정적 자바스크립트 파일에서 미발견 요리의 이름·설명·효과·조리법·재료를 알 수 없게 한다. 개인이 발견한 요리는 기존처럼 전체 정보를 제공하고, 전 서버 최초 발견 요리는 공개 도감에 필요한 최소 정보만 제공한다.

## 정보 공개 규칙

- 개인 발견 요리: 이름, 이미지, 조리 분야와 방식, 효과, 필요 재료를 포함한 전체 레시피를 제공한다.
- 전 서버 최초 발견 요리: 이름, 이미지, 최초 발견자, 발견 시각만 제공한다. 발견 시각은 정렬에만 사용한다.
- 미발견 요리: 전체 개수와 익명 자리표시자만 제공한다. ID를 포함해 카탈로그 항목과 연결할 수 있는 정보는 제공하지 않는다.
- 보유·판매 중인 완성 음식: 사용자가 실제로 볼 수 있는 음식에 한해서 이름과 효과 등 표시용 정보를 제공한다.

## 서버 경계

전체 요리 카탈로그는 서버 전용 모듈로 고정한다. `/api/v2/cooking`은 전체 `recipes`와 원시 최초 발견 행을 제거하고 다음 안전 DTO만 반환한다.

- `recipeTotal`
- `knownRecipes`
- `publicDiscoveries`
- 현재 사용자에게 필요한 보유 음식 표시 정보

전광판과 서버 소식은 최초 발견 이벤트를 기록할 때 공개 가능한 요리 이름을 페이로드에 넣는다. 클라이언트가 전체 카탈로그를 가져와 ID를 이름으로 바꾸지 않는다.

## 클라이언트 구조

- 주방 도감은 `knownRecipes`와 `recipeTotal`로 발견 카드와 익명 자리표시자를 구성한다.
- 공개 발견 탭은 서버가 정제한 `publicDiscoveries`만 사용한다.
- 캐릭터 요리 도감은 상태 API가 제공하는 개인 발견 요약만 사용한다.
- 음식 인벤토리·거래소·우편은 해당 화면에 실제로 등장한 음식의 표시 DTO만 사용한다.
- 카탈로그를 참조하던 공용 도우미는 카탈로그 독립적인 타입·표시 함수와 서버 전용 조회 함수로 분리한다.

## 검증과 방어선

- API 회귀 테스트에서 미발견 대표 요리의 ID·이름·설명·효과가 직렬화된 응답에 없는지 확인한다.
- 개인 발견 레시피와 공개 최초 발견 DTO가 허용된 필드만 갖는지 확인한다.
- 빌드 후 `.next/static/chunks`를 검사해 미발견 대표 요리의 ID와 이름이 있으면 실패시키는 스크립트를 둔다.
- 관련 화면 테스트, 타입 검사, 린트와 실제 프로덕션 빌드를 실행한다.
- 배포는 수행하지 않는다.
