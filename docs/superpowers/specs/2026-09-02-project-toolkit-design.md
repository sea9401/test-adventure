# 프로젝트 콘텐츠 툴킷 설계

## 목적

반복되는 콘텐츠 개발 절차를 프로젝트 내부의 재사용 가능한 툴킷으로 묶는다. 현재
저장소에는 이미지 검사, 권리 장부, 시뮬레이션, 배포 등 74개의 개별 스크립트가 있지만,
신규 콘텐츠 한 건은 여전히 여러 등록부·테스트·이미지·검증·GitHub 흐름을 사람이 직접
연결해야 한다. 최근 미개척지 개인 보스 추가는 52개 파일을 변경했다. 병목은 개별 도구의
부재보다 이 도구들을 콘텐츠 작업 단위로 조율하는 상위 계층의 부재다.

툴킷은 다음 전체 흐름을 하나의 재개 가능한 작업으로 관리한다.

`작업 생성 → 골격 생성 → 기믹 구현 → 이미지 준비 → 빠른 검증 → 전체 검증 → 커밋 → PR → 테스트 배포`

첫 완성형 어댑터는 최근 반복 작업이 집중된 미개척지 개인 보스로 한다. 공통 코어는
미개척지에 종속되지 않으며 이후 장비, 몬스터, NPC, 퀘스트와 다른 콘텐츠 어댑터가 같은
파이프라인을 사용한다.

## 확정된 방향

- 인자형 CLI를 단일 실행 코어로 사용하고 같은 명령을 호출하는 대화형 안내 모드를 제공한다.
- 하나의 거대한 생성기가 아니라 공통 코어, 콘텐츠 어댑터, 파이프라인과 템플릿을 분리한다.
- 첫 버전은 공통 코어와 미개척지 개인 보스 어댑터를 끝까지 완성한다.
- 반복 가능한 등록·골격·검증·배포 추적은 자동화하고 고유 전투 기믹은 직접 구현한다.
- 생성 결과는 멱등적이어야 하며 중단하거나 실패한 작업은 해당 단계부터 재개한다.
- 로컬 커밋과 외부 변경을 구분하고 푸시·PR·병합·배포에는 명시적 승인을 요구한다.
- 첫 버전의 배포 대상은 테스트 서버뿐이며 운영 배포 기능은 넣지 않는다.

다음 항목은 첫 버전에 포함하지 않는다.

- 모든 기존 콘텐츠 종류를 동시에 지원하는 어댑터 모음
- 자연어 또는 YAML만으로 고유 전투 기믹 전체를 생성하는 범용 DSL
- 운영 배포, 운영 점검 모드, 롤백과 `main` 병합 자동화
- 툴킷 전용 웹 서비스, 별도 데이터베이스 또는 관리자 화면
- 기존 74개 스크립트의 일괄 재작성
- 사용자가 작성한 임의 코드의 자동 덮어쓰기나 자동 수정

## 선택한 접근

### 프로젝트 툴킷과 어댑터

프로젝트 내부에 단일 `toolkit` 실행기를 두고 어댑터가 콘텐츠별 차이를 제공한다. 공통 코어는
작업 상태, 파일 출력, 검증 선택, 승인과 외부 실행을 관리한다. 첫 어댑터인
`unexplored-boss`는 개인 보스 명세, 생성 대상과 콘텐츠 전용 검증 규칙만 소유한다.

독립 생성 스크립트를 계속 추가하는 방식은 시작 비용이 작지만 현재 스크립트 파편화를
반복한다. 범용 콘텐츠 DSL은 장기적으로 유연하지만 고유 기믹 예외와 초기 유지비가 크다.
따라서 어댑터 방식이 현재 저장소에서 확장성, 안전성과 구현 비용의 균형이 가장 좋다.

`toolkit/`은 버전 관리하는 실행 코드다. `.toolkit/work/`는 로컬 작업 상태이므로 Git에서
제외한다. 제품 런타임은 `toolkit/`을 import하지 않으며 툴킷은 개발 의존성과 Node 실행
환경만 사용한다.

## 사용 인터페이스

두 인터페이스는 같은 명령 모델과 워크플로 코어를 호출한다.

```bash
# 사람이 사용하는 안내 모드
npm run toolkit

# Codex와 CI가 사용하는 결정론적 CLI
npm run toolkit -- content create unexplored-boss --spec boss.yaml
npm run toolkit -- task resume <task-id>
npm run toolkit -- verify fast <task-id>
npm run toolkit -- verify full <task-id>
npm run toolkit -- task approve <task-id> deploy-test --target staging --reason <text>
npm run toolkit -- release pr <task-id>
npm run toolkit -- release deploy-test <task-id>
```

대화형 모드는 질문의 답을 명령 모델로 바꿀 뿐 별도 로직을 갖지 않는다. CI에서는 대화형
프롬프트를 사용하지 않는다. 비대화형 명령에 필요한 인자가 없으면 추측하지 않고 사용법과
누락 항목을 반환한다.

모든 명령은 기본적으로 `--dry-run`을 지원한다. 생성과 수정 명령의 dry run은 예상 파일과
diff 요약을 출력하고 작업 파일, Git, GitHub와 서버를 변경하지 않는다. 조회와 검증 명령은
본래 비파괴적이므로 dry run 여부와 관계없이 동일하게 실행할 수 있다.

## 어댑터 계약

공통 코어는 콘텐츠 종류를 알지 않는다. 각 어댑터는 다음 계약을 구현한다.

```ts
type ToolkitAdapter<TSpec> = {
  id: string;
  specVersion: number;
  parseSpec(input: unknown): TSpec;
  plan(context: AdapterContext, spec: TSpec): ArtifactPlan;
  validateGenerated(context: AdapterContext, spec: TSpec): ValidationIssue[];
  selectFastChecks(context: AdapterContext, spec: TSpec): CheckDefinition[];
  selectFullChecks(context: AdapterContext, spec: TSpec): CheckDefinition[];
};
```

- `parseSpec`은 알 수 없는 키, 중복 ID, 잘못된 확률·경로·수치와 지원하지 않는 명세 버전을
  거부한다.
- `plan`은 생성 또는 수정할 파일과 각 파일의 소유 영역을 선언할 뿐 직접 쓰지 않는다.
- `validateGenerated`는 생성 후 도메인 불변식과 미구현 확장점을 검사한다.
- `selectFastChecks`와 `selectFullChecks`는 공통 검증 실행기에 기존 프로젝트 명령을 제공한다.
- 어댑터는 Git 명령, GitHub API와 배포 명령을 직접 호출하지 않는다.

어댑터 출력은 구조화된 `ArtifactPlan`으로 반환한다. 공통 파일 작성기가 dry run, 충돌 검사,
해시와 원자적 쓰기를 일관되게 처리한다.

## 작업 명세

작업 명세는 사람이 읽을 수 있는 YAML로 저장하되 어댑터의 엄격한 스키마 검사를 거친다.
명세 자체는 생성 코드가 아니며 프로젝트 타입을 직접 import하지 않는다. 첫 버전의 개인
보스 명세는 다음 범주를 포함한다.

- 메타데이터: 작업 ID, 명세 버전, 보스 ID와 이름
- 카탈로그: 연결 풀, 기준 능력치, 이미지 경로, 표시 특성
- 소환: 소환석 ID, 재료, 골드와 거래 가능 여부
- 기믹 골격: 상태 종류, 저장 필요 여부, 상태 UI 필요 여부
- 보상: 드롭, 제작 가능 여부, 장비 ID·슬롯·등급·수치
- 진행: 칭호, 업적과 보스 정복 수
- 이미지: 용도, 대상 경로, 크기 프로필과 권리 출처
- 검증: 시뮬레이션 대상, 추가로 필요한 집중 테스트

확률은 `0~1`, 비용과 수량은 안전한 음이 아닌 정수, 모든 ID는 해당 카탈로그의 명명 규칙을
따른다. 장비·이미지 파일명은 AGENTS.md의 식별자 규칙과 일치해야 한다. 프로젝트에 이미
존재하는 ID와 경로는 명시적인 업데이트 모드가 아니면 거부한다.

고유 전투 규칙은 명세의 자유 형식 코드나 표현식으로 받지 않는다. 명세는 기믹 모듈의 이름과
필요한 상태 표면만 선언하며 실제 규칙은 생성된 순수 모듈과 테스트에서 직접 구현한다.

## 미개척지 개인 보스 어댑터

### 자동 생성과 연결

어댑터는 명세에서 다음 반복 작업을 계획한다.

- 개인 보스·소환석·미개척지 진행 등록
- 장비 카탈로그, 드롭, 제작 레시피와 보상 연결
- 칭호와 업적 등록
- 기믹 순수 모듈과 집중 테스트 골격
- ATB 통합을 위한 명시적 확장점
- 세션 상태 직렬화·API 응답 확장점
- 목록·상세·전투 결과 상태 컴포넌트와 테스트 골격
- 전투 기록 표시 확장점
- 협동 보스 시뮬레이션 대상과 기준 메트릭 등록
- 이미지 경로와 권리 장부 후보 항목

기존 중앙 파일을 통째로 템플릿에서 재생성하지 않는다. 가능한 등록부는 안정된 정렬 규칙을
가진 구조화 편집기로 갱신한다. 구조화 편집이 안전하지 않은 기존 파일은 명시적으로 이름 붙인
생성 영역 또는 단일 확장점만 사용한다. 해당 영역 밖의 파일 내용이 예상 구조와 다르면
자동 수정하지 않고 충돌로 중단한다.

### 직접 구현 영역

개발자는 주로 다음 두 파일에 고유 규칙을 구현한다.

```text
src/adventure/v2/combat/<bossName>Mechanic.ts
src/adventure/v2/combat/<bossName>Mechanic.test.ts
```

ATB, API와 UI에 기믹별 코드가 필요한 경우 어댑터는 작은 타입 기반 확장점을 생성한다.
생성기는 전투 로직을 추측하지 않는다. 플레이어·보스 동시 사망, 다단 공격, 지속 피해,
세션 재개, 손상 상태 정규화와 같은 예외는 직접 작성한 테스트로 확정한다.

생성 골격은 빌드 가능한 가짜 구현을 넣지 않는다. 명시적인 미구현 마커와 실패 테스트를
만들고 `validateGenerated`가 마커를 찾으면 전체 검증, PR과 배포를 차단한다. 미구현 마커는
기믹 모듈과 집중 테스트에만 존재하며 여러 등록 파일에 흩어지지 않는다.

## 작업 상태와 재개

작업 상태는 `.toolkit/work/<task-id>/state.json`에 저장한다.

```ts
type ToolkitTaskState = {
  schemaVersion: 1;
  taskId: string;
  adapterId: string;
  specPath: string;
  specHash: string;
  baseRef: string;
  baseSha: string;
  phase: ToolkitPhase;
  approvals: Record<ExternalAction, ApprovalRecord | null>;
  steps: Record<string, StepState>;
  artifacts: ArtifactRecord[];
  external: {
    branch?: string;
    commits?: string[];
    prNumber?: number;
    prUrl?: string;
    ciRunId?: number;
    deployRunId?: number;
    deployedSha?: string;
  };
};
```

각 단계는 입력 해시, 실행한 명령, 시작·종료 시각, 결과, 생성 산출물 해시와 실패 요약을
기록한다. 성공 단계는 입력 해시와 산출물 해시가 모두 같을 때만 재사용한다. 명세 또는 입력
파일이 바뀌면 영향을 받는 단계와 그 이후 단계만 무효화한다.

`resume`은 마지막 실패 또는 대기 단계부터 시작한다. 외부 실행 ID가 있으면 새 PR이나 배포를
만들기 전에 기존 상태를 조회한다. 프로세스 종료, 네트워크 단절 또는 CI 대기 중단은 외부
작업을 중복 생성하지 않는다.

상태 파일에는 비밀값, 토큰, SSH 키, 전체 환경 변수와 명령의 민감한 출력을 저장하지 않는다.
승인은 행동 종류, 승인 시각, 대상 환경과 승인 근거만 기록한다.

## 파일 생성과 충돌 처리

공통 파일 작성기는 다음 규칙을 적용한다.

1. 계획된 모든 파일의 현재 해시와 예상 변경을 계산한다.
2. dry run에서 대상, 생성·수정 종류와 diff 요약을 보여준다.
3. 새 파일은 이미 존재하면 동일한 생성 산출물인지 확인한다.
4. 기존 파일 수정은 어댑터가 선언한 소유 영역 또는 구조화 편집만 허용한다.
5. 이전 생성 해시와 현재 해시가 다르면 사용자 수정으로 판단해 덮어쓰지 않는다.
6. 모든 충돌 검사가 끝난 뒤 임시 파일과 원자적 rename으로 한 단계의 출력을 반영한다.
7. 중간 실패 시 이미 존재하던 파일을 부분 상태로 남기지 않는다.

같은 명세와 같은 기준 SHA에서 두 번 실행한 두 번째 결과는 빈 diff여야 한다. 멱등성 검사는
툴킷 자체 통합 테스트와 각 어댑터 fixture 테스트에 포함한다.

## 이미지 파이프라인

이미지 생성 자체는 기존 이미지 생성 기능을 사용한다. 툴킷은 프롬프트 입력과 생성 결과의
검수 결정을 대신하지 않고, 승인된 결과를 프로젝트에 반입한 이후의 반복 절차를 관리한다.

1. 명세에서 식별자 기반 대상 경로와 카테고리 프로필을 확정한다.
2. 입력 이미지가 있으면 파일 형식, 크기와 알파 요구사항을 검사한다.
3. 신규 카테고리는 `scripts/optimize-images.mjs`의 프로필 존재 여부를 검사한다.
4. 기존 `npm run optimize-images`를 호출해 WebP로 변환한다.
5. `npm run check-images`로 누락·고아 참조를 검사한다.
6. 작업 명세와 생성 세션 근거로 권리 장부 후보를 만들고 사람이 확정한다.
7. `npm run check-asset-rights`로 최종 검증한다.

이미지 파일 내용의 해시가 바뀌지 않으면 최적화와 권리 검증의 성공 결과를 재사용한다.
이미지 생성 실패나 시각적 부적합은 자동 재시도하지 않고 `image-review-required` 상태로
멈춘다. 사용자가 새 이미지를 제공하면 이미지 단계부터 재개한다.

## 검증 파이프라인

### 빠른 검증

빠른 검증은 피드백 시간을 줄이기 위한 개발 단계다. 어댑터가 변경 대상과 기믹 특성에 따라
다음을 선택한다.

- 생성기·스키마·멱등성 검사
- 변경된 등록부와 기믹의 집중 Vitest
- 변경된 TypeScript 파일의 타입 검사 또는 저장소 표준 타입 검사
- 변경 파일 대상 ESLint
- 이미지가 바뀐 경우 이미지·권리 검사
- 보스 시뮬레이션의 작은 결정론적 표본

빠른 검증 성공은 완료나 배포 가능 상태를 뜻하지 않는다.

### 전체 검증

전체 검증은 최종 변경을 원격에 올리거나 PR을 준비하기 전에 다음을 모두 실행한다. 개발 중
로컬 체크포인트 커밋은 성공한 빠른 검증과 계획 파일만 포함한다는 조건으로 허용한다. 이후
입력이 바뀌면 이전 전체 검증 성공은 무효화되므로 최종 원격 작업 전에는 반드시 다시 통과해야
한다.

- `npm run check-images`
- `npm run check-asset-rights`
- `npx tsc --noEmit`
- 저장소 전체 ESLint 정책
- `npm test`
- 어댑터가 요구하는 결정론적 시뮬레이션
- 관련 기능 플래그를 적용한 `npm run build`
- `git diff --check`
- 미구현 마커, 충돌과 미등록 산출물 검사

메모리 옵션이나 기능 플래그처럼 저장소에서 이미 필요한 실행 환경은 검증 정의에 명시해 매번
재발견하지 않게 한다. 명령, 종료 코드와 요약은 작업 상태에 기록하되 긴 전체 로그는 지정된
로컬 로그 파일에 두고 상태 파일에는 경로와 해시만 보관한다.

## Git과 외부 승인

외부 상태를 바꾸는 작업은 공통 승인 모듈을 반드시 통과한다.

| 행동 | 기본 허용 | 추가 조건 |
| --- | --- | --- |
| 파일 계획·생성·검증 | 예 | 작업 범위 내부 |
| 로컬 체크포인트 커밋 | 예 | 빠른 검증 성공, 계획된 파일만 stage |
| 원격 push | 아니요 | 명시적 push 승인 |
| PR 생성·수정 | 아니요 | 명시적 PR 승인 |
| staging 병합 | 아니요 | 명시적 병합 또는 테스트 배포 승인 |
| 테스트 서버 배포 | 아니요 | 명시적 테스트 배포 승인 |
| `main` 병합·운영 배포 | 지원하지 않음 | 첫 버전 명령 자체가 없음 |

승인은 `task approve`가 작업 상태에 행동, 대상 환경, 시각과 근거를 기록한 뒤에만 유효하다.
명령행의 불리언 플래그만으로 승인하지 않으며 다른 작업이나 환경의 승인을 재사용하지 않는다.
대화형 모드도 승인 없이 기본값으로 진행하지 않는다.

하나의 명시적 테스트 배포 승인은 같은 작업을 테스트 서버에 전달하는 데 필요한 push, PR 생성,
`staging` 병합과 배포를 함께 허용한다. 이는 매 단계마다 같은 질문을 반복하지 않기 위한 종합
승인이다. 승인 범위는 해당 작업 ID와 `staging`에만 한정되며 `main`, 운영 서버, 점검 모드와
다른 PR에는 효력이 없다. 사용자가 PR까지만 요청하면 push와 PR만 허용하고 병합·배포는
허용하지 않는다.

PR 생성과 테스트 배포 진입은 현재 입력에 대한 전체 검증이 성공해야 한다. 승인 기록은 검증을
생략하거나 실패를 무시하는 권한을 주지 않는다.

툴킷은 현재 브랜치에 다른 변경이 있거나 기준 SHA가 이동했으면 stage·push·병합을 중단한다.
격리 작업공간은 프로젝트 정책에 따라 `/tmp` 아래에 만들며 기존 작업공간의 변경을 가져오거나
삭제하지 않는다.

## PR과 테스트 배포 파이프라인

PR 파이프라인은 다음 정보를 한 번 계산해 작업 상태에 보존한다.

- 기준 브랜치와 SHA
- 기능 브랜치와 최종 커밋 SHA
- 전체 검증 요약
- 변경된 콘텐츠, 이미지와 알려진 수동 구현 영역
- 테스트 서버 전용 여부

테스트 배포 승인이 있으면 다음 순서만 허용한다.

1. 기능 PR의 base가 `staging`인지 확인한다.
2. PR CI의 모든 필수 검사가 성공할 때까지 기존 실행 ID를 추적한다.
3. 승인된 병합 방식으로 `staging`에 병합한다.
4. 갱신한 `origin/staging`의 정확한 SHA를 기록한다.
5. 해당 SHA의 staging CI 성공을 확인한다.
6. 그 성공 이벤트가 만든 `deploy-staging.yml` 실행을 추적한다.
7. 배포 워크플로의 공개 표면 검증 성공을 확인한다.
8. `https://test.msmsge.com/api/health`의 애플리케이션·DB 상태를 확인한다.
9. `/api/version`의 `buildId`가 기록한 staging SHA와 정확히 같은지 확인한다.

어느 단계든 실패하면 자동 재실행, 다른 SHA 병합 또는 운영 배포로 우회하지 않는다. 작업 상태에
실패 지점과 실행 ID를 저장하고 해당 단계에서 멈춘다. 워크플로 표시용 `headSha`와 실제 배포
대상 SHA가 다를 수 있으므로 최종 판정은 staging SHA와 공개 `buildId`의 일치로 한다.

## 오류 보고

모든 오류는 다음 구조로 사람이 바로 조치할 수 있게 출력한다.

- 실패 단계와 작업 ID
- 실패 명령 또는 도메인 규칙
- 관련 파일과 안전한 수정 범위
- 이미 성공해 재사용되는 단계
- 재개 명령
- PR·CI·배포 같은 외부 실행 ID와 URL

검증 실패는 첫 실패만 숨기지 않고 같은 단계의 독립적인 정적 문제를 모아 보여준다. 파일 충돌,
승인 누락과 외부 실행 실패는 서로 다른 오류 코드로 구분한다. 비밀값과 명령의 민감한 환경은
오류 출력에서도 제거한다.

## 테스트 전략

### 공통 코어

- 명세·작업 상태 스키마 버전과 손상 상태 거부
- 단계 입력 해시와 선택적 무효화
- 성공 단계 재사용과 실패 단계 재개
- 원자적 파일 쓰기와 사용자 수정 충돌
- dry run 무변경 보장
- 승인 대상·환경 불일치 거부
- 외부 실행 ID 재사용과 중복 PR·배포 방지

### 미개척지 보스 어댑터

- 최소·전체 명세 parsing과 잘못된 확률·ID·경로 거부
- fixture 저장소에서 예상 등록부·골격 생성
- 같은 명세의 두 번째 실행이 빈 diff인지 확인
- 기존 ID, 사용자 수정과 예상 밖 중앙 파일 구조에서 안전하게 중단
- 미구현 기믹 마커가 전체 검증과 릴리스를 차단
- 생성 결과가 기존 카탈로그·이미지·권리 검사를 통과

### 파이프라인

- 가짜 command runner로 성공·실패·중단·재개 순서를 검증
- 빠른 검증이 변경 범위에 맞는 명령만 고르는지 검증
- 전체 검증이 필수 명령을 빠뜨리지 않는지 검증
- 가짜 GitHub 응답으로 PR CI, staging CI와 배포 실행 연결 검증
- 공개 버전이 예상 SHA와 다르면 성공 워크플로여도 실패 처리

실제 GitHub, 테스트 서버와 이미지 생성 서비스는 단위 테스트에서 호출하지 않는다. 테스트 배포
통합 검증은 명시적으로 승인된 실제 콘텐츠 작업에서만 수행한다.

## 구축 순서

### 1. 공통 코어

CLI 명령 모델, 대화형 래퍼, 작업 상태, 해시, 파일 계획·충돌 처리, command runner와 어댑터
계약을 구현한다. fixture 작업공간에서 멱등성과 재개를 먼저 검증한다.

### 2. 미개척지 개인 보스 수직 통합

현재 개인 보스 구현의 반복 등록 지점을 어댑터로 연결한다. 보스 하나의 예제 명세가 생성부터
집중 테스트 골격까지 완주하도록 만들고 고유 기믹은 두 집중 파일에 남긴다.

### 3. 이미지와 검증

기존 이미지 최적화·참조·권리 검사와 빠른·전체 검증을 공통 단계로 감싼다. 기존 스크립트는
재작성하지 않고 명령 실행 결과를 상태에 연결한다.

### 4. PR과 테스트 배포

Git 상태 검사, 로컬 커밋, 승인된 push·PR, CI 추적과 테스트 배포 SHA 검증을 연결한다. 운영
배포 관련 명령이 노출되지 않는지 정책 테스트로 확인한다.

각 단계는 앞 단계의 공개 계약만 사용한다. 미개척지 어댑터가 공통 코어 내부 구현을 import하지
않도록 package export 또는 명시적 모듈 경계를 둔다.

## 완료 기준

- 같은 기준 SHA와 명세로 재실행한 결과가 빈 diff다.
- 프로세스를 중단해도 마지막 실패 또는 대기 단계부터 재개한다.
- 신규 개인 보스의 반복 등록·경로·테스트 골격을 사람이 여러 파일에 직접 작성하지 않는다.
- 고유 기믹 구현과 핵심 회귀 테스트가 소수의 집중된 파일에 모인다.
- 빠른 검증과 전체 검증의 목적과 성공 의미가 분리된다.
- 이미지 참조, 최적화와 권리 장부 누락을 PR 전에 차단한다.
- 툴킷이 PR, CI와 테스트 배포 실행 ID를 보존하고 실제 staging SHA를 끝까지 추적한다.
- 사용자의 명시적 승인 없이는 push, PR, 병합과 배포가 일어나지 않는다.
- 테스트 배포 성공은 공개 health와 정확한 `buildId` 일치까지 포함한다.
- 첫 버전에는 `main`, 운영 배포와 점검 모드를 변경하는 명령이 존재하지 않는다.
- 툴킷 자체 테스트가 멱등성, 재개, 충돌, 승인과 배포 SHA 불일치를 검증한다.

## 이후 확장

첫 수직 통합이 안정되면 실제 반복 빈도와 수동 변경량을 기준으로 다음 어댑터를 하나씩 추가한다.
장비 묶음, 일반 몬스터 풀, NPC·지역, 퀘스트와 요리 순서는 고정하지 않는다. 새 어댑터는 공통
코어를 변경하지 않고 명세 스키마, 산출물 계획, 도메인 검증과 검증 선택만 추가해야 한다.

공통 코어 변경이 필요하다면 두 번째 어댑터가 요구하는 실제 중복을 확인한 뒤 확장한다. 첫
버전에서 미래 콘텐츠를 추측한 범용 DSL이나 플러그인 배포 체계를 미리 만들지 않는다.
