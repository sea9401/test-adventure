# 경제 로그 쓰기 배치와 보존 처리량 설계

## 문제

운영 `economy_events`에는 최근 24시간 약 65,600건이 추가되지만, 현재 30일 만료
데이터 정리 상한은 하루 30,000건이다. 아직 테이블 생성 후 30일이 막 지나 실제 적체는
작지만 현재 유입량이 유지되면 정리 대상이 유입량보다 빠르게 쌓인다. 생활 활동 한 번이
시도와 여러 획득 이벤트를 각각 비동기 INSERT하여 짧은 순간에 커넥션 풀을 여러 번
점유하기도 한다.

생활 이벤트는 관리자 생활 텔레메트리에서 성공률, 유저별 활동 간격, 재료 획득량을
계산하고 경제 추적에서도 사용한다. 따라서 현 단계에서 원본 행을 샘플링하거나 분 단위로
합치면 이상 행동 조사 정확도가 달라진다.

## 선택한 접근

고빈도 이벤트의 행 단위 의미는 유지하고 쓰기만 짧게 모아 PostgreSQL 다중 행 INSERT로
보낸다. `life.*`와 `currency.fishing.catch`를 25ms 또는 100건 중 먼저 도달하는 조건으로
플러시한다. 거래소 체결, 보상 실패, 관리자 지급 등 감사와 즉시 후속 판정이 필요한 다른
이벤트는 기존 단건 경로를 유지한다.

이 방식은 저장 행 수 자체를 줄이지 않지만 요청당 INSERT 왕복과 순간 풀 점유를 줄인다.
원본 행이 유지되므로 기존 관리자 집계, 경제 추적, 일일 보고의 의미와 스키마를 바꾸지
않는다. 분 단위 집계나 샘플링은 배치 적용 후 실제 부하와 이상탐지 정확도를 비교한 뒤
별도 변경으로 판단한다.

## 배치 동작

- 프로세스 안에 하나의 best-effort 큐를 두고 최대 100건씩 직렬 플러시한다.
- 첫 이벤트가 들어오면 25ms 타이머를 예약하고 타이머는 프로세스 종료를 붙잡지 않는다.
- 100건에 도달하면 타이머를 취소하고 즉시 플러시한다.
- 플러시 중 들어온 이벤트는 다음 배치에서 처리하며 동시에 두 INSERT를 실행하지 않는다.
- INSERT 실패 시 해당 배치는 기존 단건 로그와 동일하게 게임 요청을 실패시키지 않고
  오류만 남긴다. 무한 재시도나 무제한 메모리 적체는 만들지 않는다.
- 지연 플러시는 요청별 런타임 프로파일러 문맥 밖에서 실행한다. 여러 요청의 이벤트를 한
  쿼리로 합친 결과를 최초 요청 한 건의 쿼리로 잘못 귀속하지 않기 위해서다.
- `DATABASE_URL`이 없는 빌드·테스트 환경에서는 기존처럼 기록을 생략한다.

## 보존 처리량

경제 로그만 별도 일일 배치 상한 24회를 사용한다. 삭제 배치 크기 5,000건은 유지하므로
한 번의 일일 크론에서 최대 120,000건을 정리할 수 있다. 현재 약 65,600건/일 대비
약 1.8배의 여유를 확보한다. 다른 테이블의 삭제 반복 횟수는 기존 상한을 유지해 한 번의
크론이 불필요하게 길어지지 않게 한다.

30일 보존기간, 행별 감사 데이터, 스토리지 경고 기준은 변경하지 않는다.

## 검증

- 배치 큐가 지연 시간 안의 이벤트를 한 번에 쓰고, 크기 상한에서 즉시 플러시하는지
  검증한다.
- 플러시 중 유입과 쓰기 실패 뒤 후속 배치가 유실·교착 없이 처리되는지 검증한다.
- 고빈도 이벤트만 배치되고 거래·보상 등 나머지는 기존 단건 기록을 사용하는지 검증한다.
- 백그라운드 플러시가 요청 프로파일 문맥을 벗어났다가 호출자 문맥을 복원하는지 검증한다.
- 경제 로그 일일 삭제 용량이 100,000건 이상인지 정책 테스트로 고정한다.
- 관련 단위 테스트, 타입 검사, 린트, 전체 테스트와 프로덕션 빌드를 실행한다.

- 배포와 점검 모드 변경
- 로그 샘플링, 집계 테이블 또는 외부 로그 저장소 도입
- 보존기간 변경과 기존 데이터의 수동 대량 삭제
