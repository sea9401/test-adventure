# 내용수정신고 배포 게이트 설계

## 목표

등급분류 결정 이후의 모든 운영 배포에서 실행자가 게임 내용 변경 여부를 검토하고,
판단 근거와 신고 정보를 GitHub Actions 실행 기록에 남기게 한다. 신고가 필요하지만
접수 정보가 없는 변경은 운영 서버 전송 전에 차단한다.

## 접근 방식

주석이나 문서만 추가하는 방식은 배포자가 읽지 않아도 실행할 수 있어 제외한다. 별도
외부 규제 관리 시스템은 현재 규모에 비해 과도하므로 도입하지 않는다. 대신 기존 수동
`deploy.yml`에 구조화된 입력과 검증 스크립트를 추가하고, 검증 결과를 실행 요약에 남긴다.

## 입력 계약

- `content_modification_status`: `not-applicable`, `technical-only`, `reported` 중 하나를
  필수 선택한다.
- `content_modification_summary`: 검토한 변경과 판단 근거를 필수 입력한다.
- `content_modification_report_reference`: `reported`일 때 접수번호나 신고 기록 위치를
  필수 입력한다. 다른 상태에서는 선택 사항이다.

`not-applicable`은 등급 결정 이후 게임 내용 변경이 없는 배포, `technical-only`는 게임
내용 변경 없이 기술적 보완·개선만 있는 배포, `reported`는 내용수정신고를 접수한 배포를
뜻한다. 신고가 필요하지만 접수하지 않은 상태는 선택지로 제공하지 않는다.

## 검증과 기록

저장소의 독립 실행형 Node.js 스크립트가 상태값, 비어 있지 않은 요약, `reported` 상태의
접수 참조를 검증한다. 실패하면 `verify-main-ci` 작업에서 종료하므로 산출물 다운로드와
EC2 전송이 시작되지 않는다. 성공하면 상태, 요약, 접수 참조, 배포 SHA를
`GITHUB_STEP_SUMMARY`에 기록한다. 입력값의 줄바꿈과 표 구분자는 요약 형식을 깨지 않도록
정규화한다.

## 운영 문서

운영 변경 체크리스트는 배포 전 내용수정신고 판단과 배포 후 접수 기록 보존을 명시한다.
공식 안내의 핵심 기준인 게임 내용 변경 후 24시간 이내 신고 검토와 기술적 보완 예외를
함께 적되, 자동화가 법적 판단을 대신한다고 표현하지 않는다.

## 검증

회귀 테스트는 검증 스크립트를 실제 프로세스로 실행해 허용 상태, 누락된 요약, 잘못된
상태, `reported`의 접수 참조 누락, 실행 요약 기록을 확인한다. 기존 운영 보안 표면
테스트는 워크플로가 세 입력을 전달하고 서버 전송 전에 검증을 실행하는지 확인한다.

## 범위 밖

- 내용수정신고의 자동 제출
- 게임콘텐츠등급분류위원회 계정·인증정보 저장
- 운영 배포, 점검 모드 변경 또는 기존 배포 순서 변경
- 과거 패치의 신고 대상 여부에 대한 자동 법률 판단
