# 웹 카드 결제 및 무슨 코인 충전 설계

- 작성일: 2026-09-04
- 상태: 사용자 승인 완료, 구현 전
- 결제 채널: 웹사이트
- 결제대행사: 토스페이먼츠 직접 연동

## 1. 배경

현재 무슨 코인 상점에는 코인 패키지와 충전 UI가 있지만 실제 결제 기능은 연결되어
있지 않다. 운영 환경에서는 유료 서비스 정책과 결제 기능이 확정될 때까지 상점이
비공개로 유지된다. 현재 코인 잔액은 `savesKv`의 `museun-coin-wallet.v1`에 합계만
저장되므로, 유료 충전분과 게임 보상분을 구분하거나 충전 건별 환불 가능 잔액을
추적할 수 없다.

웹에서 카드 결제를 받아 무슨 코인을 충전하되, 결제 승인과 코인 지급의 중복을
막고 유료·무료 코인 및 환불 이력을 감사 가능한 형태로 보존해야 한다.

## 2. 목표

- 토스페이먼츠 일반결제창으로 웹 카드 결제를 제공한다.
- 서버가 상품과 금액을 결정하고 토스 승인 결과를 검증한다.
- 결제 승인 한 건당 코인을 정확히 한 번 지급한다.
- 화면에는 합계 잔액을 유지하면서 서버에서는 유료·무료 코인을 분리한다.
- 무료 코인을 먼저 사용하고, 유료 코인은 오래된 충전 건부터 사용한다.
- 미사용 충전 건의 전액 취소와 일부 사용 건의 관리자 검토를 지원한다.
- 결제, 지급, 사용, 취소 이력을 삭제하지 않는 원장으로 남긴다.
- 타임아웃, 중복 요청, 웹훅 재전송, 부분 실패를 복구할 수 있게 한다.
- 테스트 모드와 운영 모드를 분리하고 운영 상점은 별도 출시 준비가 끝날 때까지
  비공개로 유지한다.

## 3. 제외 범위

- Google Play Billing, Apple 인앱결제 및 앱 내 대체결제
- 구독과 자동결제
- 해외 통화 및 해외 카드 전용 결제
- 카드번호, CVC 등 결제수단 원문 저장
- 카드사와의 직접 개별 연동
- 이번 설계 승인만으로 운영 결제 활성화 또는 배포 수행

## 4. 확정 상품

기존 `MUSEUN_COIN_PACKAGES`를 서버 상품 카탈로그로 사용한다.

| 상품 ID | 지급 코인 | 결제 금액 |
| --- | ---: | ---: |
| `coin_1000` | 1,000 | 10,000원 |
| `coin_2000` | 2,000 | 20,000원 |
| `coin_3000` | 3,000 | 30,000원 |
| `coin_5000` | 5,000 | 50,000원 |

클라이언트는 상품 ID만 제출한다. 지급 코인과 결제 금액은 서버 카탈로그에서 다시
조회하며 클라이언트가 제출한 금액을 신뢰하지 않는다. 가격 변경은 기존 주문에
영향을 주지 않도록 주문 생성 시점의 상품 ID, 코인 수량, 원화 금액을 주문에
스냅샷으로 저장한다.

## 5. 선택한 접근 방식

전용 관계형 결제 주문·코인 계정·원장 테이블을 추가한다. 기존 `savesKv`에 결제
결과만 덧붙이는 방식은 환불 가능 잔액과 중복 이벤트를 안정적으로 추적하기 어렵고,
별도 결제 서버는 현재 규모에 비해 운영 부담이 크므로 사용하지 않는다.

기존 코인 변동 경로는 공통 코인 계정 서비스로 모은다. 전환 시 기존
`museun-coin-wallet.v1` 잔액은 모두 무료 코인으로 이관한다. 호환 기간에는 관계형
계정의 합계를 기존 지갑 값에도 같은 DB 트랜잭션에서 반영하되, 새 결제 기능이
활성화되는 시점부터 관계형 계정과 원장을 원본 데이터로 취급한다.

## 6. 구성 요소

### 6.1 결제 UI

기존 `MuseunCoinShopView`의 충전 모달을 확장한다.

- `결제 준비 중` 버튼을 패키지별 실제 원화 결제 버튼으로 교체한다.
- 버튼을 누르면 서버에서 주문을 만든 뒤 토스 결제창을 연다.
- 결제 성공 화면은 URL 매개변수만으로 성공을 표시하지 않고 서버 승인 완료 응답을
  확인한 뒤 잔액을 갱신한다.
- 취소, 인증 실패, 승인 대기 및 복구 중 상태를 서로 다른 문구로 안내한다.
- 최근 결제 내역과 환불 요청 진입점을 충전 모달에서 제공한다.
- 중복 클릭을 막되 새로고침 후에는 기존 주문 상태를 다시 조회할 수 있게 한다.

### 6.2 서버 API

아래 책임을 분리한 Route Handler를 둔다. 구체적인 파일명은 구현 계획에서 현재 API
명명 규칙에 맞춰 확정한다.

- 주문 생성: 로그인, 상점 접근 권한, 요율 제한, 상품 ID를 검증하고 `READY` 주문을
  만든다.
- 결제 승인: 주문 소유자와 주문 스냅샷을 검증하고 토스 승인 API를 호출한다.
- 주문 조회: 현재 사용자의 주문 상태와 안전한 결제 표시 정보만 반환한다.
- 결제 내역: 현재 사용자에게 본인 주문만 반환한다.
- 환불 요청: 미사용 건은 전액 취소 흐름으로, 일부 사용 건은 관리자 검토 흐름으로
  보낸다.
- 토스 웹훅: 이벤트를 복구 신호로만 사용하고 토스 조회 API로 실제 상태를 재확인한다.
- 관리자 API: 주문 조회, 환불 승인·거절, 재조정 실행 및 감사 사유 기록을 담당한다.

모든 API는 기존 `ensureUser` 및 관리자 권한 패턴을 사용한다. 서버 전용 모듈만 토스
시크릿 키를 읽을 수 있다.

### 6.3 토스 결제 어댑터

토스 HTTP 호출은 작은 서버 전용 어댑터 뒤에 격리한다.

- 결제 승인
- 결제 조회
- 전액 및 부분 취소
- 응답을 내부 결제 상태로 정규화
- 타임아웃과 재시도 가능 오류를 명확히 구분

Route Handler와 코인 서비스는 토스 응답 원문 구조에 직접 의존하지 않는다. 테스트는
어댑터를 대체해 성공, 거절, 타임아웃 및 모호한 응답을 재현한다.

### 6.4 코인 계정 서비스

코인 잔액을 읽고 변경하는 유일한 서버 진입점이다.

- 무료·유료 잔액 및 합계를 반환한다.
- 무료 지급, 유료 충전, 상품 사용, 환불 회수를 원장 이벤트로 기록한다.
- 상품 사용 시 무료 잔액을 먼저 차감한다.
- 부족분은 생성 시각이 오래된 유료 충전 로트부터 차감한다.
- 동일 이벤트 키를 두 번 적용하지 않는다.
- 기존 상점 구매, 길드 문장 구매 및 무료 코인 보상 경로를 이 서비스로 전환한다.

화면과 기존 API에는 필요한 경우 합계만 반환한다. 유료·무료 세부 잔액과 충전 로트는
환불 및 관리자 화면에서만 최소한으로 노출한다.

## 7. 데이터 모델

구현 시 프로젝트의 Drizzle 명명 규칙과 외래 키 정책을 따른다.

### 7.1 결제 주문

결제 주문에는 다음 정보를 저장한다.

- 내부 UUID와 외부 노출용 `orderId`
- 사용자 ID
- 상품 ID, 지급 코인, 결제 원화 금액 스냅샷
- `READY`, `CONFIRMING`, `PAID`, `CANCEL_PENDING`, `PARTIALLY_CANCELED`,
  `CANCELED`, `FAILED`, `REVIEW_REQUIRED` 상태
- 토스 `paymentKey`와 승인 상태
- 생성, 승인, 취소 및 최종 갱신 시각
- 실패 코드와 운영자 확인용 정규화 메시지

`orderId`와 값이 존재하는 `paymentKey`에는 각각 고유 제약을 둔다. 카드번호나 CVC를
저장하지 않으며, 카드사·결제수단처럼 고객 지원에 필요한 토스의 비민감 표시 정보만
최소 보관한다.

### 7.2 코인 계정과 불변 원장

사용자별 코인 계정은 `freeBalance`, `paidBalance`, 합계 및 갱신 시각을 가진다. 원장은
다음 내용을 append-only로 기록한다.

- 사용자 ID
- 고유 이벤트 키
- 이벤트 종류와 원천 주문 또는 게임 보상 ID
- 무료 코인 증감
- 유료 코인 증감
- 적용 후 잔액 스냅샷
- 생성 시각과 안전한 감사 메타데이터

이벤트 키에는 고유 제약을 둬 같은 승인, 지급, 사용 또는 취소가 재전송돼도 한 번만
반영되게 한다.

### 7.3 유료 코인 로트와 사용 배분

승인된 충전 주문마다 지급량, 사용 가능량, 환불 처리 중 보류량을 가진 유료 코인
로트를 만든다. 유료 코인을 사용하는 원장 이벤트는 어느 로트에서 몇 코인을
차감했는지 배분 내역을 남긴다. 이 정보로 특정 충전 건의 미사용 수량과 부분 환불
가능 금액을 계산한다.

### 7.4 환불 요청

환불 요청에는 대상 주문, 요청자, 요청 코인과 원화 금액, 사유, 상태, 처리자, 처리
시각 및 토스 취소 식별자를 기록한다. 사용자와 관리자 작업은 모두 감사 이력에 남긴다.

## 8. 결제 데이터 흐름

1. 사용자가 로그인한 상태에서 코인 패키지를 선택한다.
2. 서버가 카탈로그를 조회해 `READY` 주문을 만들고 `orderId`, 상품명, 금액, 지급량 및
   런타임용 토스 클라이언트 키를 반환한다.
3. 브라우저는 토스 SDK로 결제 인증을 시작한다.
4. 성공 리다이렉트 후 브라우저가 `paymentKey`, `orderId`, `amount`를 서버 승인 API에
   전달한다.
5. 서버는 주문 소유자, 상태, 주문 금액 및 전달 금액을 확인한다. 일치하지 않으면
   승인하지 않는다.
6. 서버는 주문을 조건부로 `CONFIRMING`으로 바꾸고 `paymentKey`를 보존한 뒤 토스 승인
   API를 호출한다.
7. 토스가 `DONE` 상태와 정확한 주문·금액을 반환하면 하나의 DB 트랜잭션에서 주문을
   `PAID`로 바꾸고, 유료 코인 로트와 원장 이벤트를 만들고, 코인 계정 및 호환 지갑을
   갱신한다.
8. 브라우저는 서버 주문 조회 결과가 `PAID`일 때만 결제 성공과 새 잔액을 표시한다.

승인 호출 결과가 타임아웃으로 불명확하면 같은 결제를 즉시 다시 지급하지 않는다.
`paymentKey`로 토스 상태를 조회해 `DONE`이면 7단계의 멱등 지급을 수행하고, 실패가
확정되면 주문을 `FAILED`로 바꾼다. 자동 판단이 불가능하면 `REVIEW_REQUIRED`로 남기고
관리자 화면에서 재조정한다.

## 9. 코인 사용 흐름

1. 상품 구매 API가 코인 계정 행을 잠근다.
2. 무료 코인을 가능한 만큼 먼저 차감한다.
3. 부족분을 오래된 유료 로트부터 차감하고 배분 내역을 만든다.
4. 코인 차감, 상품 지급, 원장 기록 및 호환 지갑 갱신은 하나의 DB 트랜잭션으로
   완료한다.
5. 어느 단계든 실패하면 코인과 상품 지급을 모두 롤백한다.

기존 `museun-coin-wallet.v1`의 직접 수정 경로를 남기지 않도록 관련 서버 경로를 공통
서비스로 전환한 뒤 결제를 활성화한다.

## 10. 환불 흐름

### 10.1 전혀 사용하지 않은 충전 건

- 사용자 요청 시 해당 로트의 전체 잔액을 보류해 사용을 차단한다.
- 서버가 토스 전액 취소 API를 호출한다.
- 취소 성공 후 주문 상태, 유료 코인 회수, 원장 및 호환 지갑을 반영한다.
- 실패가 확정되면 보류를 해제한다. 결과가 모호하면 조회로 재조정할 때까지 보류한다.

### 10.2 일부 사용한 충전 건

- 즉시 자동 취소하지 않고 관리자 검토 요청을 만든다.
- 관리자는 약관과 실제 사용 배분을 확인해 환불 가능 수량과 원화 금액을 결정한다.
- 승인 시 환불 대상 잔여 코인을 보류하고 토스 부분 취소 API를 호출한다.
- 성공 후 부분 취소 원장과 잔여 로트를 반영한다.

### 10.3 외부 취소와 지급 후 분쟁

토스에서 먼저 취소 또는 지급 취소가 관측되면 내부 주문과 원장을 재조정한다. 이미
사용해 회수 가능한 유료 코인이 부족한 경우 임의로 무료 코인을 음수로 만들지 않고,
계정을 `REVIEW_REQUIRED`로 표시해 추가 유료 코인 사용과 환불을 제한하고 관리자가
처리한다.

최종 환불 가능 범위와 고지 문구는 온라인게임 표준약관, 전자상거래 관련 법령 및 PG
계약 심사를 반영해 운영 활성화 전에 별도 검토한다. 구현은 확정 정책을 바꾸더라도
원장과 환불 승인 규칙만 수정할 수 있게 분리한다.

## 11. 오류 처리와 보안

- 토스 시크릿 키는 접두사 `NEXT_PUBLIC_`가 없는 서버 런타임 환경변수로만 읽는다.
- 공개 가능한 클라이언트 키도 서버 주문 응답으로 전달해 테스트·운영 모드를 런타임에
  분리한다.
- 주문 생성, 승인, 조회, 환불에는 인증·소유권 검사와 사용자/IP 요율 제한을 적용한다.
- 승인 전 서버 카탈로그, 주문 스냅샷, 리다이렉트 금액 및 토스 조회 결과를 비교한다.
- 웹훅 payload만으로 코인을 지급하거나 회수하지 않는다.
- 결제·환불 이벤트에 고유 멱등 키를 사용한다.
- 로그에 시크릿 키, 전체 인증 헤더, 카드 원문 또는 불필요한 개인정보를 기록하지
  않는다.
- CSP와 외부 연결 허용 목록은 토스 공식 SDK·결제창에 필요한 출처만 추가한다.
- 결제 및 공급 기록은 관련 법령상 요구되는 기간을 충족하도록 최소 5년 보존한다.
- 사용자에게는 내부 오류와 토스 원문 오류를 그대로 노출하지 않고 재시도 가능 여부와
  고객 문의용 주문번호를 제공한다.

## 12. 운영 모드와 출시 조건

결제 상태는 기존 상점 공개 게이트와 별도의 서버 전용 설정으로 관리한다.

- `disabled`: 주문 생성과 승인 모두 차단
- `test`: 테스트 상점 키를 사용하고 내부 허용 계정만 접근
- `live`: 운영 키와 심사 승인된 상점 정보를 사용

기본값은 `disabled`다. 테스트 구현 중에도 기존 `NEXT_PUBLIC_MUSEUN_COIN_SHOP_OPEN`의
운영 값은 변경하지 않는다. `live` 설정만으로 일반 사용자에게 상점을 공개하지 않는다.

운영 활성화 전 아래 항목을 모두 확인한다.

- 토스페이먼츠 전자결제 계약, 홈페이지 및 카드사 심사 완료
- 운영 클라이언트 키·시크릿 키를 비밀 저장소에 등록
- 사업자 정보, 통신판매 관련 표시, 이용약관, 개인정보처리방침 및 환불 정책 반영
- 유료 재화 도입에 따른 게임 등급 내용수정 신고 또는 재분류 필요 여부 확인
- 운영자 환불·재조정 절차와 고객 문의 채널 준비
- 테스트 결제, 취소, 부분 실패 복구 및 정산 대조 완료
- 사용자의 별도 배포 및 상점 공개 지시 확인

운영 배포와 상점 공개는 이 설계의 자동 후속 작업이 아니다.

## 13. 관리자 기능

- 주문번호, 사용자, 상품, 금액, 지급 코인, 현재 상태로 검색
- 토스 상태와 내부 상태 비교
- 승인·지급이 불명확한 주문의 안전한 재조정
- 환불 요청 승인·거절 및 사유 기록
- 충전 로트 잔여량과 사용 배분 조회
- 전체·부분 취소 실행 전 영향 미리보기와 재확인
- 모든 관리자 작업을 기존 관리자 감사 로그에 기록

관리자는 잔액을 임의 덮어쓰지 않는다. 수정이 필요하면 사유가 포함된 별도 원장
이벤트를 생성한다.

## 14. 테스트 전략

### 14.1 단위 테스트

- 서버 상품 ID와 가격 스냅샷 검증
- 무료 우선, 유료 FIFO 차감
- 유료 로트 사용 배분과 환불 가능 잔액 계산
- 주문 및 원장 상태 전이
- 토스 오류의 내부 오류 정규화

### 14.2 Route Handler 테스트

- 비로그인, 타 사용자 주문, 비공개 상점 접근 차단
- 변조된 금액 및 알 수 없는 상품 거절
- 같은 `orderId`·`paymentKey` 동시 승인 시 한 번만 지급
- 성공, 거절, 타임아웃, 재조회 복구
- 중복 웹훅과 순서가 뒤바뀐 웹훅
- 전액 취소, 부분 취소, 취소 실패 및 모호한 결과
- 요율 제한과 안전한 오류 응답

### 14.3 DB 통합 테스트

- 동시 승인과 동시 상품 구매에서 잔액 불변식 유지
- 결제 주문, 원장, 로트, 계정 및 상품 지급의 원자성
- 기존 지갑의 무료 잔액 이관과 호환 미러 검증
- 고유 제약에 의한 멱등성 검증

### 14.4 UI 및 E2E

- 충전 모달의 키보드·스크린리더 접근성
- 결제 성공, 사용자 취소, 인증 실패, 승인 대기 화면
- 새로고침 후 주문 복구와 잔액 갱신
- 최근 결제 내역 및 환불 요청
- 토스 테스트 상점으로 실제 과금 없는 결제·취소 흐름 수동 확인

## 15. 완료 기준

- 테스트 모드에서 네 가지 코인 패키지를 카드 결제로 인증·승인할 수 있다.
- 서버 검증을 통과한 승인만 코인을 지급한다.
- 같은 결제 이벤트를 반복해도 코인이 한 번만 지급된다.
- 무료·유료 잔액과 합계, 유료 로트 및 원장이 모든 변동 후 일치한다.
- 기존 코인 사용 기능이 공통 계정 서비스를 통해 정상 동작한다.
- 미사용 건 전액 취소와 일부 사용 건 관리자 검토 흐름이 동작한다.
- 타임아웃과 웹훅 재전송을 재조정할 수 있다.
- 관련 자동화 테스트와 토스 테스트 상점 점검을 통과한다.
- 운영 상점은 비공개이며 어떤 환경에도 배포되지 않은 상태로 구현 결과를 인계한다.
