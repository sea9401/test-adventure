# 기록 기반 게임 내용 변경 배포 설계

## 목적

게임 내용이 바뀐 운영 배포마다 변경 내역을 저장소에 남기되, 실제 내용수정신고 여부는
운영자가 별도로 판단할 수 있게 한다. 내부 기록을 공식 신고 접수로 잘못 표현하지 않으며,
기록 누락 상태로 운영 배포가 진행되지 않게 한다.

## 상태 모델

기존 `not-applicable`, `technical-only`, `reported` 상태는 의미를 바꾸지 않는다.
새 `recorded` 상태는 게임 내용 변경을 저장소에 기록했지만 공식 신고 여부는 아직 운영자
판단 대상으로 남아 있다는 뜻이다.

- `recorded`: `docs/content-modification-records/*.md` 아래의 추적 가능한 문서 경로 필수
- `reported`: 실제 접수번호 또는 신고 기록 위치 필수
- `not-applicable`: 게임 내용 변경 없음
- `technical-only`: 게임 내용 변경 없는 기술적 보완

`recorded`는 `reported`의 대체 표현이 아니며 공식 신고 완료를 의미하지 않는다.

## 검증과 배포 흐름

운영 배포 입력에 내부 기록 경로를 추가한다. 독립 검증 스크립트는 `recorded` 상태에서
경로가 허용된 문서 디렉터리 안의 Markdown 파일인지, 실제 체크아웃에 존재하는 일반
파일인지 확인한다. 절대 경로, 상위 디렉터리 이동, 다른 디렉터리와 존재하지 않는 파일은
거부한다.

검증에 성공하면 Actions 실행 요약에 배포 SHA, 상태, 변경 요약, 내부 기록 경로와 공식
신고 참조를 각각 구분해 남긴다. 이 검증은 기존처럼 운영 산출물 조회와 서버 전송보다
먼저 실행한다.

## 이번 변경 기록

미개척지 콘텐츠 운영 승격은 별도 기록 문서로 남긴다. 문서에는 테스트 서버 출처,
운영에 보존한 변경, 천공 포격 상향, 미개척지 보스 전 능력치 상향, 검증·롤백 기준과
공식 신고 판단이 보류 상태라는 사실을 기록한다. 이후 운영자가 신고가 필요하다고 판단하면
동일 문서에 접수 참조를 추가할 수 있다.

## 테스트

검증 스크립트 회귀 테스트는 정상 내부 기록을 허용하고, 누락·존재하지 않는 경로·경로
이탈·잘못된 확장자를 거부하는지 확인한다. 기존 세 상태와 `reported` 접수 참조 검증도
그대로 통과해야 한다. 운영 보안 표면 테스트는 새 워크플로 입력과 검증 순서를 고정한다.

## 범위 밖

- 공식 내용수정신고 자동 제출
- 운영자를 대신한 법적 분류 판단
- 기존 등급 표시 또는 이용 정책 변경
- 점검 모드 자동 해제
