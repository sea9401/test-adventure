# 요리 일괄 제작 설계

## 목표

요리 도감에서 한 번에 1~20개의 조리 수량을 선택하고 단 한 번의 API 요청으로 제작한다. 일괄 조리 결과는 기존에 1개씩 같은 횟수만큼 조리한 것과 동일하게 각 음식의 품질을 독립적으로 판정해, 반복 요청으로 요청 제한에 걸리는 문제를 줄이면서 기존 품질 확률과 경제 밸런스를 유지한다.

## 현재 상태와 선택지

서버의 `craft` 동작은 이미 `quantity`를 받아 최대 20개까지 재료·준비 세트·경험치·통계를 한 트랜잭션에서 처리하지만, 도감 UI는 항상 `quantity: 1`만 전송한다. 또한 서버는 수량 전체에 품질을 한 번만 판정하므로 이 기능을 그대로 노출하면 한 번의 걸작 판정이 최대 20개에 동시에 적용된다.

검토한 방식은 다음과 같다.

1. 기존 `craft` 요청을 사용하고 서버에서 수량별 품질을 독립 판정한다. 한 요청과 한 트랜잭션을 유지하면서 반복 조리와 같은 품질 분포를 보존하므로 이 방식을 채택한다.
2. 클라이언트에서 선택 수량만큼 기존 1개 요청을 반복한다. 서버 변경은 적지만 요청 제한 문제를 해결하지 못하므로 제외한다.
3. 별도의 일괄 조리 엔드포인트를 추가한다. 기존 `craft`가 이미 수량을 지원해 API와 트랜잭션 로직만 중복되므로 제외한다.

## UI

- 발견한 각 레시피 카드에 `조리 수량` 숫자 입력을 둔다.
- 입력 범위는 서버 제한과 같은 정수 1~20이며 기본값은 1이다.
- 레시피별 입력값을 독립적으로 유지해 한 카드의 선택이 다른 카드에 영향을 주지 않는다.
- 조리 버튼은 선택값을 포함해 `N개 조리`로 표시하고 `{ action: "craft", recipeId, quantity: N, usePrepSet }` 한 건만 전송한다.
- 준비 세트를 켜면 기존 규칙대로 선택 수량만큼 필요하다는 안내를 유지한다. 재료나 준비 세트가 부족하면 서버가 현재 오류 메시지로 요청 전체를 거부한다.
- 기존 불투명 `SURFACE_CARD`와 `SURFACE_INSET`, 라이트·다크 입력 배경을 유지한다.

## 서버 처리와 응답

- 요청 수량 검증과 최대 20개 제한, 재료 절감 누적치 계산, 준비 세트 차감, 경험치 및 숙련도 계산은 기존 흐름을 유지한다.
- 원조 여부와 전문 분야 보너스는 레시피 단위로 한 번 계산하되, 품질은 요청 수량만큼 `rollCookingQuality`를 호출한다.
- 품질별 결과를 해당 `CookingFoodId` 재고에 각각 합산한다.
- `dishesCooked`는 총수량만큼, `masterpiecesCooked`는 실제 걸작 수량만큼 증가시킨다.
- 응답의 `result`에는 `qualityCounts`를 `{ normal, careful, masterpiece }` 형태로 담는다. 기존 1개 조리 소비자를 위해 수량이 1일 때의 `quality`와 `foodId`도 계속 제공한다.
- 클라이언트 완료 알림은 하나의 품질 문자열 대신 실제 생성된 품질별 수량을 한국어로 요약한다.
- 재료·준비 세트 부족이나 검증 실패 시 트랜잭션 전체가 취소되어 일부 수량만 제작되지 않는다.

## 테스트

- API 회귀 테스트는 고정된 난수열로 여러 개를 조리해 일반·정성작·걸작이 각각 올바른 재고로 쌓이고, 걸작 통계와 총 조리 수량이 정확한지 확인한다.
- 단일 조리는 기존 `quality`와 `foodId` 응답 호환성을 유지하는지 보호한다.
- 도감 컴포넌트 테스트는 수량 입력을 변경했을 때 한 번의 mutation에 해당 수량이 전달되고 버튼 문구가 갱신되는지 확인한다.
- 잘못된 범위는 기존 서버 검증 테스트로 보호하고 관련 테스트, TypeScript, ESLint, 이미지 참조 검사와 diff 검사를 실행한다.

## 범위 제외

- 조건 납품은 이미 수량 입력과 단일 요청을 지원하므로 변경하지 않는다.
- 상시 납품의 일괄 판매, 최대 제작 가능 수량 자동 계산, 조리 상한 20개 확대는 이번 변경에 포함하지 않는다.
- 배포와 점검 모드 변경은 수행하지 않는다.
