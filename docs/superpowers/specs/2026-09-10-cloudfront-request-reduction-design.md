# CloudFront 요청량 1차 절감 설계

## 문제와 근거

2026년 9월 1일부터 9일까지 운영 Nginx 로그에는 하루 평균 약 130만 건의 요청이
기록됐다. 공격성 스캐너 경로는 전체의 약 0.02%에 불과했고, 정상 게임 API가 대부분을
차지했다. 특히 `/api/v2/me/rare-maps`는 9월 9일에 92,192건으로 두 번째로 많았다.

사냥터 페이지는 `GameStateProvider` 상태가 바뀔 때 다시 렌더되며, 라우트 페이지에서
`onEnterRareMap`, `onReturnToNormalHunt`, `onSelectRareMap` 콜백을 인라인으로 만든다.
희귀 지도 조회 effect가 이 콜백 객체 자체를 의존성으로 사용하기 때문에 사냥 결과처럼
상위 상태가 바뀔 때마다 같은 GET을 다시 실행한다. 숨겨진 탭에서도 presence와 제재 확인
인터벌이 계속 요청을 보내는 별도 낭비도 확인했다.

## 선택한 방식

이번 1차 변경은 사용자에게 보이는 갱신 주기와 게임 규칙을 바꾸지 않고 요청의 잘못된
재실행만 제거한다.

1. `V2DungeonFloorView`의 희귀 지도 조회는 `rareMapIid`와 희귀 지도 진입 기능의 활성
   여부가 바뀔 때만 실행한다. 만료 처리 콜백은 ref로 최신 값을 참조해 콜백 객체가 새로
   만들어져도 조회를 다시 시작하지 않는다.
2. `V2DungeonList`의 희귀 지도 조회는 `onSelectRareMap` 객체가 아니라 기능 활성 여부만
   의존한다.
3. presence 및 제재 상태의 정기 인터벌은 문서가 보이는 동안에만 요청한다. 탭이 다시
   보이면 기존처럼 즉시 한 번 동기화한다.

## 고려한 대안

- 모든 폴링 간격을 일괄적으로 늘리면 구현은 간단하지만 채팅·알림·접속자 표시가 늦어지고
  요청 폭증의 실제 원인인 effect 재실행은 남는다.
- 알림·우편·공지용 통합 API를 새로 만들면 추가 절감이 가능하지만 인증, DB 조회 함수
  추출, 공유 클라이언트 상태가 함께 바뀐다. 이번 원인 제거를 검증한 뒤 별도 2차 변경으로
  진행한다.
- `rare-maps` 응답을 전역 시간 캐시하면 화면 간 이동 요청도 줄지만 지도 사용·삭제 직후
  오래된 보유 상태를 보여줄 수 있다. 우선 불필요한 재실행만 제거한다.

## 오류 처리와 동작 보존

- 네트워크 실패는 기존처럼 조용히 무시하거나 다음 주기에 재시도한다.
- 숨겨진 탭에서 최초 제재 조회가 실패한 경우의 보안 재시도는 유지한다. 중단 대상은 정상
  상태를 확인한 뒤의 정기 인터벌뿐이다.
- 희귀 지도 ID가 실제로 바뀌면 반드시 새로 조회하고, 만료 지도면 최신
  `onReturnToNormalHunt` 콜백으로 복귀한다.

## 테스트

- 희귀 지도 화면과 사냥터 목록을 새 콜백 객체로 재렌더해도 GET이 한 번만 실행되는 회귀
  테스트를 먼저 실패시킨다.
- `rareMapIid`가 바뀌면 새 조회가 실행되고 최신 만료 콜백을 호출하는 기존 동작을 보존한다.
- fake timer와 `visibilityState`를 사용해 숨겨진 탭에서는 presence 및 제재 정기 요청이
  발생하지 않고, visible 복귀 시 즉시 한 번 실행되는지 검증한다.

## 범위 밖

- 낚시 체크포인트와 자동사냥 주기 변경
- 채팅·피드·알림 갱신 간격 변경
- 통합 chrome 상태 API
- CloudFront 플랜 변경 및 운영 배포
