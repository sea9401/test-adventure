# CloudFront 요청 절감 2차 설계

## 목표

CloudFront Pro 월간 Requests 허용량을 소모하는 반복 요청 중 1차에서 다루지 않은 전역 폴링과 정적 자산 재검증을 줄인다. 사용자가 화면을 보고 있을 때의 핵심 체감은 유지하고, 숨김 탭과 장시간 변화가 없는 화면의 요청 간격만 늘린다.

이번 변경은 로컬 코드 최적화까지만 수행한다. AWS 플랜 변경, CloudFront 동작 변경, 운영 배포는 범위 밖이다.

## 현재 문제

- 상단바 한 곳에서 일반 알림, 우편, 새 공지를 각각 60초마다 조회한다. 같은 인증 사용자 상태를 확인하는 데 CloudFront viewer request가 세 번 발생한다.
- `public/`의 이미지와 앱 아이콘은 Next.js 기본값인 `Cache-Control: public, max-age=0`으로 매번 재검증된다. 운영 CloudFront 기본 동작은 캐시 비활성이라 304도 요청 허용량을 소모한다.
- 닫힌 채팅은 변화가 없어도 30초마다, 전쟁 전광판은 30초마다 계속 조회한다.

## 설계

### 1. 상단 상태 요청 통합

`GET /api/v2/chrome-status`를 추가한다. 인증을 한 번 수행한 뒤 다음 값을 한 응답으로 반환한다.

```json
{
  "ok": true,
  "notificationUnread": 0,
  "mailUnread": 0,
  "hasUnreadNotice": false
}
```

서버의 `readChromeStatus(userId)`는 기존 세 API와 같은 판정 규칙을 사용한다.

- 일반 알림: 읽지 않은 저장 알림(복권 알림 제외) + 아직 확인하지 않은 수확 준비 알림
- 우편: 읽지 않았고 수신자가 삭제하지 않았으며 차단 관계로 가려지지 않은 받은 우편
- 공지: 최신 전체 공지 한 건을 사용자가 열람했는지 여부

응답은 사용자별 데이터이므로 `Cache-Control: private, no-store`를 명시한다. 기존 상세 목록 API는 유지해 알림 미리보기, 우편함, 공지 목록 동작을 바꾸지 않는다.

클라이언트에는 `ChromeStatusProvider`를 게임의 영속 chrome에 한 번 마운트한다. Provider가 최초 조회, 보이는 탭에서 60초 폴링, 숨김 탭이 다시 보일 때 즉시 조회를 담당한다. `v2notif:read`, `v2inbox:refresh`, `bulletin:read` 이벤트도 동일한 통합 요청으로 처리한다. 중복 이벤트나 느린 네트워크에서도 동시에 두 요청을 실행하지 않는다.

`NotificationBell`과 `V2NoticeLink`는 Provider 상태를 소비한다. 알림 미리보기에서 상세 데이터를 받은 경우와 항목을 낙관적으로 읽음 처리한 경우에는 Provider 카운트도 갱신한다. 독립 렌더 테스트와 재사용을 위해 Provider 밖에서는 초기값을 표시하되 별도 폴링은 하지 않는다.

### 2. 정적 자산 브라우저 캐시

Next.js 16 문서에 따라 `next.config.ts`의 `headers()`로 다음 공개 자산에 브라우저 캐시를 부여한다.

- `/images/:path*`
- `/icon-192.png`
- `/icon-512.png`
- `/favicon.ico`
- `/manifest.webmanifest`

정책은 `public, max-age=86400, stale-while-revalidate=604800`이다. 이 프로젝트의 공개 이미지 파일명은 콘텐츠 해시가 아니므로 `immutable` 1년 캐시는 사용하지 않는다. 하루 안에는 브라우저가 요청 자체를 생략하고, 그 뒤에는 갱신하면서 최대 7일간 stale 응답을 활용할 수 있다.

`/sw.js`는 새 서비스 워커 배포를 놓치면 안 되므로 기존 `no-cache, no-store, must-revalidate`를 그대로 유지한다. 이번 설정은 현재 CloudFront의 CachingDisabled 동작을 바꾸지 않으며, 주된 효과는 재방문 브라우저의 viewer request 감소다.

### 3. 채팅·전광판 적응형 폴링

채팅 패널이 열려 있을 때는 기존 3초 간격을 유지한다. 닫힌 채팅은 연속으로 새 메시지가 없을 때 다음 단계로 늦춘다.

- 초기 및 변화 직후: 30초
- 3회 연속 무변화: 60초
- 10회 연속 무변화: 120초

새 전역·거래·길드 메시지가 하나라도 오면 30초 단계로 즉시 복귀한다. 숨김 탭에서는 예약을 제거하고 다시 보일 때 즉시 조회한다.

전쟁 전광판도 재귀 `setTimeout` 방식으로 바꿔 요청 중첩을 막고, 사건 ID 묶음이 연속으로 같을 때 다음 단계로 늦춘다.

- 초기 및 변화 직후: 30초
- 2회 연속 무변화: 60초
- 6회 연속 무변화: 120초

새 사건이 오면 30초로 복귀한다. 네트워크 오류는 데이터가 변하지 않았다는 증거가 아니므로 idle 횟수를 늘리지 않고 현재 단계로 재시도한다. 숨김 탭은 중단하고 focus/visible 복귀 시 즉시 동기화한다.

## 오류 처리와 호환성

- 통합 상태 조회가 실패하면 마지막으로 성공한 배지 상태를 유지하고 다음 주기 또는 이벤트에서 회복한다.
- 인증 실패는 새 API에서 401을 반환한다.
- 상세 알림/우편/공지 API와 이벤트 이름은 유지한다.
- 적응형 폴링은 요청 결과가 정상일 때만 idle 단계를 변경한다.
- 공개 자산은 최장 하루 동안 이전 버전이 보일 수 있다. 자산을 즉시 교체해야 할 때는 파일명을 바꾸는 방식으로 캐시를 우회할 수 있다.

## 검증

- 통합 상태 서버 계산과 API의 인증·응답·캐시 헤더 테스트
- Provider의 단일 요청, 60초 폴링, hidden 중단, visible 복귀, 세 이벤트 통합 테스트
- `NotificationBell`과 `V2NoticeLink`가 Provider 값을 표시하는 회귀 테스트
- 채팅과 전광판의 단계별 지연 정책 단위 테스트
- 정적 자산 헤더 설정 테스트
- 관련 테스트, lint, TypeScript, production build 실행

## 기대 효과와 측정

상단 상태 폴링은 사용자당 분당 세 요청에서 한 요청으로 줄어 해당 세 경로 기준 약 3분의 2를 절감한다. 정적 자산과 적응형 폴링의 실제 절감폭은 재방문 비율과 서버 활동량에 따라 달라진다. 운영 반영 뒤 CloudFront와 Nginx의 경로별 일 요청량을 최소 24시간 비교해 다음 단계를 결정한다.
