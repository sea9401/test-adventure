# CloudFront 요청 절감 4차 설계

## 목표와 범위

1~3차 이후에도 주기적으로 CloudFront를 통과하는 서버 피드, 거래소, 협동 보스·길드·토너먼트 요청을 화면 가시성과 실제 데이터 변화에 맞춰 줄인다. 거래소 판매 화면의 진입 GET 네 건은 하나의 overview API로 합친다.

채팅의 실시간 전송 구조 변경은 사용자의 요청에 따라 제외한다. AWS 설정 변경, 운영 배포, 푸시도 하지 않는다.

## 공통 폴링 정책

고정 `setInterval` 대신 완료 시점부터 다음 실행을 예약하는 공통 visible-only 스케줄러를 사용한다.

- 요청이 진행 중일 때 추가 tick·visibility·focus 이벤트가 발생해도 겹쳐 보내지 않는다.
- 탭이 hidden이면 예약을 취소하고 요청하지 않는다.
- visible 복귀 시 즉시 한 번 동기화하고 이후 주기를 다시 예약한다.
- 성공 응답의 안정적인 snapshot이 달라지면 idle 횟수를 0으로 되돌린다.
- snapshot이 같으면 idle 횟수를 늘려 단계적으로 간격을 늘린다.
- 실패 응답은 마지막 화면 상태와 idle 단계는 유지한 채 기본 오류 처리 후 다시 예약한다.
- 응답의 현재 시각처럼 매번 달라지는 필드는 snapshot 비교에서 제외한다.

공통 스케줄러 자체를 가짜 타이머로 검증하고, 각 소비자는 endpoint·가시성·종료 조건이 제대로 연결되는지 회귀 테스트로 고정한다.

## 1. 서버 피드

`ServerFeedView`의 30초 고정 interval을 기존 `feedPollDelayMs` 정책을 쓰는 재귀 폴링으로 교체한다.

- 최신 첫 페이지는 30초에서 시작한다.
- 동일한 최신 snapshot이 2회 이어지면 60초, 6회 이어지면 120초로 늘린다.
- 새 항목이 생기면 즉시 30초로 돌아간다.
- 과거 페이지(`beforeId`가 있는 상태)는 사용자가 보고 있는 고정 기록이므로 자동 폴링하지 않는다.
- category 변경은 별도 snapshot으로 취급하고 idle 상태를 초기화한다.
- visible 복귀와 window focus의 즉시 최신화는 유지하되 in-flight 요청은 병합한다.

## 2. 거래소 목록

거래소 browse/mine 탭의 visible 10초 고정 interval을 적응형으로 바꾼다.

- 활성 상태는 10초에서 시작한다.
- 동일 snapshot이 2회 이어지면 30초, 5회 이어지면 60초로 늘린다.
- listing id, 상태, 가격·수량·입찰 정보와 내 골드처럼 화면에 영향을 주는 필드가 변하면 10초로 돌아간다.
- `serverNow`는 snapshot에서 제외한다.
- hidden 동안은 요청하지 않고 visible 복귀 시 즉시 갱신한다.
- 구매·입찰·회수 같은 mutation 뒤의 기존 즉시 refresh는 유지한다.
- mine 탭의 내 입찰 및 열린 가격 알림 표면은 browse와 같은 tick에서 함께 갱신해 별도 timer를 만들지 않는다.

## 3. 협동 보스·길드·토너먼트

공유 상태 화면은 visible일 때만 갱신하고, 변화가 없을수록 주기를 완화한다.

- 협동 보스 목록: 20초 시작, 동일 snapshot 2회 뒤 60초.
- 협동 보스 상세: 전투 중 5초 시작, 동일 snapshot 3회 뒤 15초, 8회 뒤 30초. 격파·만료 상태면 중단한다.
- 길드 레이드: 20초 시작, 동일 snapshot 2회 뒤 60초.
- 길드 거래소 공유 토큰: 공유 토큰 기능을 실제 사용하는 경우에만 10초 시작, 동일 snapshot 2회 뒤 30초, 5회 뒤 60초.
- 아레나 토너먼트: 진행 중 15초 시작, 동일 snapshot 2회 뒤 30초, 6회 뒤 60초. 완료 상태면 중단한다.

사용자 행동이 발생하면 기존처럼 즉시 서버 결과를 반영한다. visible 복귀도 즉시 갱신한다. 따라서 활발한 전투·입찰의 반응성은 유지되고 방치 화면만 느려진다.

## 4. 거래소 판매 진입 API 통합

판매 탭 진입 시 개별 호출하던 equipment, inventory, rare maps, fishing specimens 네 GET을 `/api/v2/marketplace/sell-overview` 한 건으로 바꾼다.

서버는 인증을 한 번 수행하고 필요한 save key를 `readSaves` 한 번으로 읽은 뒤 다음 데이터를 기존 parser로 구성한다.

- 보유·장착 장비
- 거래 가능한 재료와 요리 음식·정의
- 유효한 희귀 지도와 캐시 아이템
- 낚시 표본

기존 네 endpoint는 다른 화면과 호환성을 위해 유지한다. 새 route는 기존 marketplace 직렬화 규칙을 재사용하며, 클라이언트의 판매 가능 품목·장착 제외·수량 규칙은 바꾸지 않는다.

## 오류와 복구

- 조회 실패 시 이미 표시된 데이터는 유지한다.
- recursive timer는 요청 완료 뒤 하나만 재예약하므로 느린 응답도 중첩되지 않는다.
- hidden 중 발생한 변화는 visible 복귀의 즉시 요청으로 회복한다.
- 판매 overview 실패는 기존 판매 탭 오류 표면으로 전달하며 부분 응답을 적용하지 않는다.

## 검증

- 공통 adaptive visible scheduler의 간격 증가, 변화 시 초기화, hidden 중단, visible 복귀, in-flight 중복 방지 테스트
- 서버 피드의 최신 페이지만 폴링하고 30→60→120초로 완화되는 테스트
- 거래소 browse/mine의 10→30→60초 완화와 hidden 복귀 테스트
- 협동 보스·길드 레이드·공유 토큰·토너먼트의 가시성, adaptive delay, terminal 중단 테스트
- 판매 overview route와 payload 조립 단위 테스트
- 판매 탭 진입이 새 endpoint 한 건만 추가하고 기존 네 GET을 추가하지 않는 요청 테스트
- 관련 테스트, lint, TypeScript, 전체 테스트, production build

## 기대 효과

변화가 적은 장시간 열린 화면에서 서버 피드는 최대 75%, 거래소 목록은 최대 약 83%, 공유 상태 화면은 종류에 따라 약 67~75%까지 주기 요청을 줄일 수 있다. 판매 탭 진입은 네 GET에서 한 GET으로 줄어든다. 실제 절감률은 데이터 변화와 탭 체류 시간에 따라 달라지므로 운영 반영 후 CloudFront 경로별 24시간 요청량으로 확인한다.
