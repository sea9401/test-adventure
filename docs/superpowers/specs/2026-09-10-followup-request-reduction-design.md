# 후속 요청 절감 설계

## 1. 입찰 이후 조회

입찰 트랜잭션은 이미 지갑 잔액과 새 최고가·마감 시각을 반환한다. 응답에 권위 있는 입찰 횟수와 만료 시각을 추가하고 클라이언트가 해당 매물 및 공통 자원 상태를 갱신한다. 이 경로에서는 browse와 game-state 재조회를 생략한다. 이미 열린 내 입찰 내역은 별도 조회를 유지하여 내역 정렬·새 행·다른 매물 정산 상태를 보존한다. 구 서버의 불완전한 응답에는 기존 재조회를 유지한다. 정기 폴링은 그대로 다른 사용자의 변화를 반영한다.

## 2. 재방문 시 공통 시세 재사용

개인 인벤토리와 실시간 매물은 캐시하지 않는다. 모든 사용자에게 같은 참고 시세만 브라우저 메모리에서 최대 30초 재사용하고 동시에 시작한 요청을 병합한다. 서버의 기존 시세 캐시도 30초이므로 합산 지연은 최대 약 60초다. 성공한 거래소 행동 후 캐시를 무효화하고, 이전 진행 중 응답이 무효화 이후 캐시에 다시 들어오지 못하도록 세대를 구분한다. 실패는 저장하지 않는다. 탭 전환 및 화면 재마운트에서도 같은 캐시를 사용한다.

## 3. 접속 유지와 버전 확인 통합

접속 유지 POST에 `/api/version`과 동일한 배포 buildId를 추가한다. 클라이언트는 성공한 heartbeat의 buildId를 30초 이내에서 버전 검사에 재사용하고, 진행 중 heartbeat가 있으면 해당 응답에 합류한다. 동시에 시작하는 mount/복귀 이벤트는 한 microtask 뒤 heartbeat를 확인한다. heartbeat 부재·실패·구 서버 응답·만료 상태에서는 기존 version GET을 사용한다. heartbeat 자체도 진행 중 요청을 병합한다. 접속 등록 30초와 제재 확인 120초, 기기 무효화·강제 호환성 갱신·사냥 중 새로고침 보호 규칙은 유지한다.

## 대안과 제약

개인 데이터 전역 캐시는 무효화 범위가 넓고, heartbeat 간격 연장은 접속자 판정을 바꾸므로 이번에는 적용하지 않는다. 버전 확인 통합의 절감폭은 작지만 별도 DB 조회나 실시간 연결을 추가하지 않는다. 채팅, AWS 설정, 배포, 푸시와 기존 테스트 실패 수정은 범위 밖이다. 기존 tsconfig 변경을 보존하고 현재 브랜치에서 단계별 커밋한다.

## 검증

각 단계는 실패하는 회귀 테스트를 먼저 확인한다. 입찰 응답 필드·개인정보 제외·지갑과 매물 반영·GET 감소·구 응답 fallback을 검증한다. 시세 캐시는 TTL·동시 조회·오류·무효화 경쟁 및 실제 화면 재방문을 검증한다. 버전 통합은 heartbeat 합류·실패 fallback·만료·중복 방지·세션 무효화와 기존 VersionCheck 동작을 검증한다. 마지막에는 관련 통합 테스트, lint, 타입 검사 및 production build를 실행한다.
