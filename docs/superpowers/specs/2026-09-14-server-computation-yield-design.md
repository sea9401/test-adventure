# 서버 계산 중 다른 요청의 응답성 보존

## 근거와 범위

2026-09-14 22:23~22:53 KST 운영 프로파일에서 전투력 랭킹의 동기 계산은
25회, 최대 856.76ms였고 업적 랭킹은 한 번에 1,223.82ms였다. 일괄 사냥이
집중된 1분에는 1,603전의 전투 계산에 22.58초를 사용했다. 이벤트 루프의
최대 지연은 1,799.36ms였다. DB 처리 시간에는 이벤트 루프 대기가 포함될 수
있으므로 이 기록만으로 DB 자체를 병목으로 단정하지 않는다.

사용자는 **50회 일괄 사냥과 보상 유지**를 명시했고, 다른 요청에도 실행 기회를
주는 개선을 승인했다. 현재 브랜치의 동일한 계산 경로를 수정한다. 운영 SHA에는
사냥 모듈 분리가 적용되어 있지만 현재 브랜치는 `hunt/route.ts`에 루프가 있다.
관련 없는 운영 변경을 가져오거나 현재 브랜치를 교체하지 않는다.

## 선택

1. **협력적 실행 양보(선택):** 약 8ms의 실행 구간을 넘으면 판/사용자 계산 사이에
   Node `setImmediate`로 이벤트 루프에 실행 기회를 준다. 기존 결과와 트랜잭션을
   유지하면서 동기 계산이 연속해서 다른 요청을 밀어내는 문제를 완화한다.
2. Worker thread: CPU 계산을 완전히 분리할 수 있지만 전투 상태 직렬화, 빌드 산출물,
   작업 수 제한과 실패 복구 설계가 추가로 필요하다. 이번 수정에는 도입하지 않는다.
3. 캐시 TTL 연장/서버 증설: 갱신 주기나 운영 구성을 바꾸며, 단일 긴 계산의 중단 없는
   실행을 직접 해결하지 못한다. 이번 수정에는 포함하지 않는다.

## 구현 계약

- 서버 전용 공통 헬퍼가 `performance.now()`로 시간 구간을 재고, 예산을 넘었을
  때만 실제 이벤트 루프를 양보한다. `Promise.resolve()`만 사용하는 양보는 금지한다.
- 사냥 루프는 같은 요청·트랜잭션·잠금 안에서 기존 순서로 요청된 50전을 완료한다.
  지원권별 기존 상한(프리미엄 100회 포함)은 변경하지 않는다.
  첫 판 전에는 불필요하게 양보하지 않고 다음 판 시작 전에 예산을 확인한다.
  보상, RNG 호출, 재생 로그, 저장 횟수, 조기 중단 조건, 요청 제한은 그대로 둔다.
- 업적/전투력 랭킹은 후보별 점수 계산을 순차적으로 나눠 수행한다. 완성된 결과만
  기존 방식으로 정렬/캐시한다. 30초 TTL, 동시 계산 공유, 오류 후 재시도와 제외
  정책을 유지한다. 계산 도중의 부분 순위는 노출하지 않는다.
- 새 의존성, DB 마이그레이션, 프론트엔드 변경, 운영 쓰기/배포는 없다.

## 한계와 검증

한 판 또는 한 사용자 계산 자체는 동기 실행되므로 8ms는 절대 지연 상한이 아니다.
총 계산량이나 DB 쿼리 비용을 줄이는 변경도 아니다. 양보 중에는 같은 트랜잭션의
잠금이 유지되므로 부하에 따라 요청의 총 처리 시간이 늘 수 있다.

실제 이벤트 루프 콜백이 50전 종료 전 실행되는 회귀 테스트와 50전 전체 결과·보상·
잠금/저장 횟수를 확인한다. 랭킹도 계산 도중 콜백 실행, 전체 결과 정렬, 동시 cold
miss 공유와 오류 재시도를 검사한다. 로컬 비교 실험으로 실행 양보 전후의 타이머
지연과 계산 완료량을 측정한다. 운영 개선 수치는 향후 승인된 배포 뒤 같은 구간의
프로파일로 확인해야 한다.
